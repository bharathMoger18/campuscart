AWS Global Infrastructure

Regions → Availability Zones → Data Centers
Senior Engineer Says

Before you touch a single AWS service, you need to understand where your resources actually live physically. AWS is not some magic cloud — it's real servers, in real buildings, in real cities around the world.

Think of AWS infrastructure as a 3-level hierarchy: Regions contain Availability Zones, and Availability Zones contain Data Centers. Each level exists for a specific reason.

Level 1 — Regions

What is a Region?

A Region is a geographic area where AWS has deployed clusters of data centers. Each region is completely independent — a failure in Mumbai does not affect Singapore. Each region has its own networking infrastructure, power supply, and internet connectivity.

When you create an EC2 instance, you are physically placing a server in a specific region. That server does not move. Your data stays in that region unless you explicitly replicate it.

Level 2 — Availability Zones (AZs)

What is an Availability Zone?

An Availability Zone is one or more discrete data centers within a region. The key word is discrete. Each AZ has its own:

  • Independent power supply (separate utility power + UPS + generators)
  • Independent cooling system
  • Independent physical network connections to the internet
  • Physical separation from other AZs (minimum ~1km, often more)

AZs within a region are connected to each other via low-latency, high-bandwidth, private fiber. Typically < 1ms between AZs. Fast enough to replicate your database in real time across AZs.

Level 3 — Data Centers

Physical Layer

Each AZ contains multiple physical data centers. AWS does not tell you exactly how many — it's a security consideration. A single AZ might have 2–8 actual buildings. These buildings contain the physical servers your EC2 instances run on.

When you launch an EC2 instance, AWS picks a physical server in one of these buildings, installs a hypervisor (KVM-based), and runs your VM on it. Your t2.micro is literally one virtual machine sharing physical hardware with many other customers — but fully isolated via the hypervisor.

1.2

What is a VPC?

Virtual Private Cloud — Your private network inside AWS
Senior Engineer Says

Imagine you're a bank. You wouldn't put your servers in a shared office building where anyone can walk up to them. You'd rent a private, locked floor with controlled access. VPC is that private floor — inside AWS's building.

A VPC is a logically isolated section of the AWS cloud where you launch resources. "Logically isolated" means AWS uses software-defined networking to make your network completely separate from every other customer's network — even though the physical hardware is shared.

What Exactly is "Logical Isolation"?

Network Level Explanation

At the network level, AWS uses VXLAN (Virtual Extensible LAN) and custom networking hardware (called Nitro) to create overlay networks. Your VPC traffic is encapsulated in packets that are invisible to other VPCs. Even if your EC2 and another customer's EC2 are on the same physical server, their network traffic is completely separated.

Think of it like apartments in a building. You're in apartment 3A, your neighbor is in 3B. Same floor, same building, but your rooms are completely private. You can't see into their apartment, they can't see into yours.

Default VPC vs Custom VPC

Default VPC (Bad for Production)

Every AWS account gets a default VPC automatically in every region. CIDR: 172.31.0.0/16. It comes with public subnets already created, internet gateway already attached.

Problem: zero control over IP ranges, subnet layout, routing. Everything is wide open. Not suitable for production.

Custom VPC (What CampusCart Uses)

You design every aspect. CIDR block you choose: 10.0.0.0/16. Subnets you design. Route tables you control. Security groups you define.

Full control over network architecture. This is what every production system uses. This is what your resume says you did.

CIDR Notation

Classless Inter-Domain Routing — Binary level breakdown
Senior Engineer Says

CIDR notation looks scary until you understand what it actually means. Once you understand it at the binary level, you'll never be confused again. CIDR is just a way to describe a range of IP addresses.

Format: IP_ADDRESS / PREFIX_LENGTH. The slash number tells you how many bits are "fixed" (the network part). The remaining bits are "free" (the host part, which is your range of IPs).

IP Address = 32 Binary Bits

Binary Foundation

The Math — 10.0.0.0/16

/16 means: The first 16 bits are fixed (network). The remaining 16 bits are free (host).

Free bits = 16. Number of IPs = 2¹⁶ = 65,536 total IP addresses.

Range: 10.0.0.0 to 10.0.255.255. The first two octets (10.0) are fixed. The last two octets (.0.0 to .255.255) can be anything.

Breaking Down /24 (Subnet CIDR)

10.0.1.0/24 — Public Subnet 1

/24 means: First 24 bits are fixed. Only 8 bits are free.

Free bits = 8. Total IPs = 2⁸ = 256 IPs.

Range: 10.0.1.0 to 10.0.1.255. First 3 octets fixed, last octet free.

AWS Reserved IPs in Every Subnet

AWS Reserves 5 IPs from Every Subnet — Here's Why

In a /24 subnet (e.g. 10.0.1.0/24), AWS reserves these 5 addresses:

  • 10.0.1.0 — Network address (identifies the subnet itself. Not usable.)
  • 10.0.1.1 — Reserved by AWS for the VPC router. This is the default gateway for all instances in the subnet.
  • 10.0.1.2 — Reserved by AWS for DNS. The VPC DNS server always lives at base + 2.
  • 10.0.1.3 — Reserved by AWS for future use.
  • 10.0.1.255 — Broadcast address. AWS doesn't support broadcast, but still reserves it.

Usable IPs in a /24: 256 - 5 = 251 usable IPs. For a t2.micro instance, this is more than enough.

1.4

Subnets

Public vs Private — it's all about the route table
Senior Engineer Says

Here's the most important thing about subnets that most people get wrong: There is no such thing as a "public subnet" or "private subnet" at the infrastructure level. A subnet is just a range of IP addresses. What makes it public or private is which route table is attached to it.

If a subnet's route table has a route 0.0.0.0/0 → igw-xxxxxxx, it's public. If it doesn't, it's private. That's the only difference.

Why Divide a VPC into Subnets at All?

The Reason for Subnetting

Subnets give you network-level isolation within your VPC. You want different resources to have different levels of internet access:

  • Your web server (nginx/EC2) needs to be reachable from the internet → public subnet
  • Your database (PostgreSQL) should NEVER be directly reachable from the internet → private subnet
  • Your cache (Redis) same — private → private subnet

In CampusCart's Docker setup, PostgreSQL and Redis are containers — not on AWS directly. But the architecture principle is the same. If we were using AWS RDS and ElastiCache, they'd go in private subnets.

Public Subnet — What Goes Here

Has internet route → resources can send and receive traffic from the internet (if they have public IPs).

  • EC2 web servers
  • Load balancers
  • Bastion hosts (jump boxes)
  • NAT Gateways
Private Subnet — What Goes Here

No internet route → resources can only communicate within the VPC. Internet can never initiate a connection to them.

  • RDS databases
  • ElastiCache (Redis)
  • Application servers (in 3-tier arch)
  • Lambda functions (VPC-attached)

1.5

Internet Gateway

The door between your VPC and the public internet
Senior Engineer Says

Without an Internet Gateway, your VPC is a completely sealed box. Your EC2 instances can talk to each other inside the VPC, but nothing on the internet can reach them, and they can't reach the internet. It's like a LAN with no router to the outside world.

The Internet Gateway is that router. It's a horizontally scaled, redundant, highly available VPC component — meaning AWS manages it, it never goes down, and you don't pay per-hour for it (only for data transfer).

How IGW Works at Network Level

NAT and Routing — What Actually Happens

When traffic flows OUT from your EC2 (e.g., apt-get update):

  • EC2 sends packet: src: 10.0.1.x → dst: 8.8.8.8
  • Route table says: 0.0.0.0/0 → igw-xxxxxxx
  • Packet hits the IGW
  • IGW performs 1:1 NAT — replaces private IP with the Elastic IP: src: YOUR_ELASTIC_IP → dst: 8.8.8.8
  • Packet goes out to internet

When traffic flows IN (someone accesses your website):

  • Packet arrives at IGW: dst: YOUR_ELASTIC_IP
  • IGW reverse NATs: maps Elastic IP → EC2's private IP (10.0.1.x)
  • Packet delivered to EC2

Route Tables

How AWS decides where your network packets go
Senior Engineer Says

A route table is exactly what the name says — a table of routing rules. Every packet that arrives in a subnet gets checked against the route table. The route table says: "for traffic going to THIS destination, send it to THAT target."

Think of it like a postal sorting room. A packet arrives — the sorter checks the destination. If destination is internal (10.0.0.0/16) → deliver locally. If destination is external (anything else) → send to the internet gateway.

→ No 0.0.0.0/0 route = no internet access = resources here are private
Most Specific Route Wins

Route tables follow the "longest prefix match" rule. The more specific (longer) the prefix, the higher the priority.

Example: A packet going to 10.0.1.5:

  • Matches 10.0.0.0/16 (local) — 16 bits match
  • Matches 0.0.0.0/0 — 0 bits match
  • Winner: 10.0.0.0/16 (more specific) → routed locally

A packet going to 8.8.8.8 (Google DNS):

  • Does NOT match 10.0.0.0/16
  • Matches 0.0.0.0/0 — catch-all
  • Winner: 0.0.0.0/0 → sent to IGW
1.7

EC2

Elastic Compute Cloud — Virtual machines in AWS
Senior Engineer Says

EC2 stands for Elastic Compute Cloud. "Elastic" means you can scale up or down. "Compute" means it's a server with CPU and RAM. "Cloud" means it runs on AWS infrastructure. At its core, an EC2 instance is a virtual machine running on AWS's physical servers using the KVM hypervisor (via the Nitro system).

What is an AMI?

Amazon Machine Image

An AMI is a snapshot template that contains the root volume of the instance — the operating system, any pre-installed software, and configuration. When you launch an EC2, you choose an AMI. AWS takes that template and creates a fresh copy as your EBS root volume.

Think of an AMI like a Docker image — it's a read-only template. When you launch it, you get a writable running instance.

Stop vs Terminate — Critical Difference

STOP (Safe)

Like shutting down your laptop. The instance stops. EBS volumes are preserved. Data is intact. Public IP is released (but Elastic IP stays). You can restart anytime. You're only charged for EBS storage while stopped.

TERMINATE (Permanent)

Like destroying your laptop. Instance is permanently deleted. EBS root volume is deleted (by default). All data is gone. Cannot be undone. Elastic IP is disassociated (and starts costing money if not released).

What is EBS?

Elastic Block Store — The Hard Drive

EBS is the persistent storage attached to your EC2. It's a network-attached block device — like a USB hard drive, but over the network. When you stop and restart an EC2, the same EBS volume is reattached. Your files, Docker images, volumes — all persist on EBS.

For CampusCart: we use a 20GB gp3 EBS volume. gp3 is the latest generation general-purpose SSD — better performance at lower cost than gp2.

✅
Why Ubuntu 22.04 LTS? LTS = Long Term Support. Canonical provides security updates for 5 years (until 2027). Ubuntu is the most widely used Linux distro in cloud environments. It's what Bharath uses locally — zero learning curve. All Docker, AWS CLI, nginx documentation uses Ubuntu examples.

SSH Key Pairs

Asymmetric cryptography — how you securely access EC2
Senior Engineer Says

SSH uses asymmetric cryptography — also called public-key cryptography. This is fundamentally different from passwords. With a password, both sides know the secret. With public-key crypto, only you have the private key. AWS only ever sees your public key.

The magic: you can prove your identity to the server using only your private key, without ever sending the private key over the network. The server verifies you by checking if your private key matches the public key it has stored.

How the SSH Handshake Works

Step by Step — Network Level
  • Step 1: You run ssh -i campuscart-key.pem ubuntu@ELASTIC_IP
  • Step 2: TCP connection established to port 22 on EC2
  • Step 3: Server sends its host key fingerprint (you verify it's the right server)
  • Step 4: Server sends a random challenge encrypted with your PUBLIC key
  • Step 5: Only YOUR private key can decrypt this challenge
  • Step 6: You send back the decrypted challenge — proving you have the private key
  • Step 7: Server verifies → SSH session established. All subsequent traffic is encrypted with a symmetric session key.

Why chmod 400 on the .pem file?

chmod 400 sets the file permissions to read-only for owner, nothing for group and others. In binary: 100 000 000.

SSH will refuse to use a private key if it's readable by anyone other than you. This is a security check. If your .pem file has permissions 644 (group/world readable), SSH throws: UNPROTECTED PRIVATE KEY FILE! and refuses to connect.

chmod 400 campuscart-key.pem # 4 = read (owner only) # 0 = nothing (group) # 0 = nothing (others) # SSH requires this. Do this IMMEDIATELY after downloading the .pem file.
1.9

Elastic IP

A static public IP that doesn't change
Senior Engineer Says

Every time you stop and start an EC2 instance, AWS assigns it a brand new public IP address. The old one goes back into the pool for other customers. This is a problem: if your DNS record points to your EC2's public IP, every restart breaks your DNS. Elastic IP solves this.

An Elastic IP is a static public IPv4 address that belongs to YOUR AWS account — not to a specific instance. You allocate it once, associate it with an instance. Even if you stop/restart the EC2, the Elastic IP stays associated with it.

❌ Without Elastic IP

EC2 gets IP: 13.232.45.67
You stop EC2 for maintenance.
EC2 restarts — new IP: 15.206.12.89
Your DNS record is stale. Users get errors.
CI/CD pipeline SSH command breaks.
Everything that depends on the IP breaks.

✅ With Elastic IP

Elastic IP allocated: 13.232.45.67
Associated to EC2.
EC2 stops → Elastic IP stays yours.
EC2 restarts → same IP: 13.232.45.67
DNS always works.
GitHub Actions SSH always works.

AWS Pricing — Important for Interviews

Elastic IPs are free when associated with a running EC2 instance. AWS charges ~$0.005 per hour (~$3.60/month) when:

  • The Elastic IP is allocated but NOT associated with any instance
  • The Elastic IP is associated with a STOPPED instance
  • You have more than 5 Elastic IPs in an account

Soldier 6 reminder: When tearing down, RELEASE the Elastic IP — don't just disassociate it. Otherwise you'll get charged $0.005/hour for nothing.

How Elastic IP Maps to the EC2

The Elastic IP is NOT literally attached to the EC2's network interface. Here's what actually happens:

  • Your EC2's private IP is always 10.0.1.x (from the subnet)
  • The Elastic IP lives at the Internet Gateway level
  • IGW maintains a 1:1 NAT mapping: Elastic IP ↔ EC2 Private IP
  • Inbound packet for Elastic IP → IGW translates → delivers to 10.0.1.x
  • Outbound packet from 10.0.1.x → IGW translates → appears to come from Elastic IP

Inside the EC2, if you run ifconfig, you will NOT see the Elastic IP. You only see the private IP. The Elastic IP is entirely handled by the IGW. This is called 1:1 NAT at the gateway level.

AWS Shared Responsibility Model

Who is responsible for what — Security in the cloud
Senior Engineer Says

The Shared Responsibility Model defines the boundary between what AWS secures and what you secure. This comes up in almost every cloud interview. The simplest way to remember it: AWS is responsible for security OF the cloud. You are responsible for security IN the cloud.

CampusCart Context — What You Own

For CampusCart, YOU are responsible for:

  • Keeping Ubuntu 22.04 patched (apt-get update && apt-get upgrade)
  • Configuring Security Groups correctly (port 80, 443 open — port 22 restricted to your IP only)
  • NOT committing .env files or secrets to GitHub
  • Using SSM Parameter Store for secrets (not hardcoding them)
  • IAM role with minimal permissions (only what EC2 needs)
  • Docker image security (not running as root inside containers)
✅
Interview Answer: "AWS secures the physical infrastructure, hypervisor, and hardware. My responsibility is everything above the hypervisor — OS patching, application security, network configuration via security groups, IAM permissions, and protecting secrets. For CampusCart, I implement this by using IAM roles (not hardcoded keys), SSM Parameter Store for secrets, and restricting SSH to my IP only in the security group."
