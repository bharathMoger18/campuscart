VPC & Networking
Q01
What is a VPC and why did you create one instead of using the default VPC?
Easy
+
A VPC (Virtual Private Cloud) is a logically isolated network that you own inside AWS. Think of it as renting a private floor in AWS's building — you control who enters, how traffic flows, and how resources are organized. Everything you deploy in AWS lives inside a VPC.

Why Not the Default VPC?

❌ Default VPC — Why We Avoided It
AWS creates one automatically in every region. CIDR: 172.31.0.0/16. All subnets are public by default. No private subnet separation. Zero control over IP architecture. Not production-appropriate.
✅ Custom VPC — What CampusCart Uses
CIDR: 10.0.0.0/16. We designed every subnet. Public and private separation. Route tables we control. Matches the architecture a real production system would have.
What to Say in the Interview

"For CampusCart, I created a custom VPC with CIDR 10.0.0.0/16 in ap-south-1 (Mumbai). The default VPC had all subnets public with no network isolation — not production-appropriate. My custom VPC gave me full control: I designed 4 subnets across 2 AZs, created separate route tables for public and private subnets, and attached an internet gateway only for the public-facing EC2 instance. This matches the architecture patterns used in real production environments."

💡
Key thing interviewers want to hear: You understand WHY the default VPC is unsuitable, not just that you created a custom one. The answer is: no private subnets, no network isolation, no control over IP architecture.
Q02
What is a CIDR block? Explain 10.0.0.0/16.
Medium
+
CIDR stands for Classless Inter-Domain Routing. A CIDR block is a notation that describes a range of IP addresses. The format is: IP_ADDRESS / PREFIX_LENGTH. The slash number tells you how many bits are fixed (network part) — the remaining bits are free (host range).

Breaking Down 10.0.0.0/16

An IPv4 address is 32 bits. Written as 4 octets (groups of 8 bits) in decimal, separated by dots.

10.0.0.0 in binary: 00001010.00000000.00000000.00000000 └─────────────────┘ └─────────────────┘ /16 = FIXED bits FREE bits (host range) (the "network" part) (your IP addresses) Free bits = 32 - 16 = 16 bits Total IPs = 2^16 = 65,536 IP addresses Range: 10.0.0.0 → 10.0.255.255

Why 10.0.0.0/16 for CampusCart?

  • RFC 1918 private range: 10.x.x.x is a private IP space — not routable on the public internet. Perfect for internal VPC use.
  • 65,536 IPs: Far more than needed now, but leaves room for any future expansion — multiple services, environments, or regions.
  • Standard practice: 10.0.0.0/16 is the most common VPC CIDR used in AWS architecture guides and production systems.

Subnet CIDRs — /24

Each of our 4 subnets uses /24, giving 256 total IPs, 251 usable (AWS reserves 5 per subnet).

What to Say in the Interview

"CIDR notation describes a range of IP addresses. The /16 means 16 bits are fixed — that leaves 16 free bits, giving us 2 to the power of 16, which is 65,536 IP addresses. We chose 10.0.0.0/16 because the 10.x.x.x range is a private RFC 1918 address space — it's not publicly routable, which is exactly what you want for an internal VPC. Each subnet gets a /24, which gives 251 usable IPs after AWS reserves 5."

Q03
What is the difference between a public and private subnet?
Medium
+
This is a trick question that most people answer wrong. There is no inherent difference at the infrastructure level. A subnet is just a range of IP addresses. What makes it "public" or "private" is entirely determined by which route table is associated with it.

The Only Real Difference — Route Table

PUBLIC SUBNET
Route table has a route:
0.0.0.0/0 → igw-xxxxxxx

Resources with public IPs can communicate with the internet. Internet can initiate connections to them.
PRIVATE SUBNET
Route table has NO internet route.
Only has:
10.0.0.0/16 → local

Resources can only talk within the VPC. Internet cannot reach them.

CampusCart Architecture Decision

  • EC2 in Public Subnet (10.0.1.0/24): nginx must be reachable from the internet on port 80/443. Must be public.
  • Private subnets (10.0.3.0/24, 10.0.4.0/24): Reserved for future database (RDS/PostgreSQL) and cache (ElastiCache/Redis). Database should NEVER be directly internet-accessible.
  • Current state: Docker containers (PostgreSQL, Redis) run on the same EC2 — they're isolated by Docker networking, not AWS subnets. If we migrate to managed services, they'd go in private subnets.
What to Say in the Interview

"The difference is purely in the route table. A public subnet has a route sending 0.0.0.0/0 traffic to the Internet Gateway, so resources can communicate with the internet. A private subnet has no such route — resources can only communicate within the VPC. For CampusCart, the EC2 instance is in a public subnet because nginx needs to serve HTTP traffic. We have two private subnets reserved for future managed database services like RDS."

⚠️
Don't say "a public subnet gives public IPs automatically." That's auto-assign public IP, a separate setting. The subnet itself being public or private is about the route table, not IP assignment.
Q04
How many usable IP addresses does a /24 subnet have in AWS?
Easy
+
A /24 has 256 total IPs (2⁸). But AWS reserves 5 specific IPs in every subnet, leaving 251 usable IPs. Knowing WHY each one is reserved is what separates a confident answer from a memorized one.

The 5 Reserved IPs — In a /24 (e.g. 10.0.1.0/24)

IP AddressReserved ForWhy
10.0.1.0Network AddressIdentifies the subnet itself. Standard networking convention.
10.0.1.1VPC RouterAWS uses this as the default gateway for all instances in the subnet.
10.0.1.2DNS ServerAWS VPC DNS always runs at base + 2. Used for Route 53 Resolver.

What to Say in the Interview

"A /24 has 256 total IPs, but AWS reserves 5 — the network address at .0, the VPC router at .1, the DNS server at .2, a future-use address at .3, and the broadcast address at .255. So each /24 subnet in CampusCart has 251 usable IPs. For our EC2 deployment, that's more than sufficient."

Q05
What is an Internet Gateway and what does it do?
Medium
+
An Internet Gateway (IGW) is the component that connects your VPC to the public internet. Without it, your VPC is a completely sealed private network — nothing in, nothing out. It is a fully managed, horizontally scaled, redundant AWS component — you don't manage it, it never fails, you don't pay hourly for it.

What It Does — At Network Level

  • Routing anchor: Route tables point 0.0.0.0/0 traffic to the IGW. The IGW then handles the actual internet routing.
  • 1:1 NAT (Network Address Translation): Your EC2 has a private IP (10.0.1.x). The IGW maps this to your Elastic IP at the gateway level. Inbound packets for the Elastic IP get translated to the private IP. Outbound packets appear to come from the Elastic IP.
  • Bidirectional: Unlike NAT Gateway, IGW allows traffic in BOTH directions — inbound from internet and outbound to internet.

CampusCart Traffic Flow Through IGW

# Inbound: User accesses CampusCart User Browser → ELASTIC_IP:80 → IGW (reverse NAT: Elastic IP → 10.0.1.x) → EC2 Private IP (10.0.1.x:80) → nginx container → serves frontend / proxies to Django # Outbound: EC2 calls external API (e.g. Stripe) Django → Stripe API (api.stripe.com) → EC2 (10.0.1.x) → Route Table → IGW → IGW (NAT: 10.0.1.x → ELASTIC_IP) → Internet → Stripe
What to Say in the Interview

"The Internet Gateway is attached to the CampusCart VPC and acts as the bridge between our private network and the public internet. It performs 1:1 NAT — mapping our EC2's private IP to the Elastic IP for inbound traffic and vice versa for outbound. Without it, the EC2 would be unreachable from the internet and couldn't make outbound calls — things like Stripe payment webhooks would fail."

Q06
What is a route table? What routes did you configure?
Medium
+
A route table is a set of rules that determines where network traffic is directed. Every subnet in a VPC must be associated with a route table. When a packet arrives in a subnet, AWS checks the route table to decide where to send it — using the longest prefix match rule.

CampusCart Route Tables

Public Route Table — associated with Public Subnet 1 and Public Subnet 2:

DestinationTargetPurpose
10.0.0.0/16localTraffic within VPC stays inside. Auto-created, cannot delete.
0.0.0.0/0igw-xxxxxxxAll other traffic → Internet Gateway. This is what makes the subnet "public".

Private Route Table — associated with Private Subnet 1 and Private Subnet 2:

DestinationTargetPurpose
10.0.0.0/16localOnly intra-VPC communication. No internet route = private.

Longest Prefix Match — How Routing Decisions Work

When two routes could match a destination, AWS picks the most specific (longest prefix). A packet to 10.0.1.5 matches both 10.0.0.0/16 (local) and 0.0.0.0/0 (IGW). The /16 is more specific, so it wins — traffic stays local. A packet to 8.8.8.8 only matches 0.0.0.0/0, so it goes to the IGW.

What to Say in the Interview

"I configured two route tables. The public route table has two routes: a local route for 10.0.0.0/16 that keeps intra-VPC traffic internal, and a 0.0.0.0/0 route pointing to the Internet Gateway for all external traffic. The private route table only has the local route — no internet access at all. This is exactly what makes the subnets public or private. AWS uses longest prefix match to decide which route wins."

Why did you use 2 availability zones?
Medium
+
Each Availability Zone is a physically separate data center with its own power, cooling, and network — within the same region. Using 2 AZs means if one data center has a catastrophic failure (power outage, fire, network cut), the other AZ is completely unaffected. This is the foundation of high availability in AWS.

Public Subnet 2 (10.0.2.0/24)
Private Subnet 2 (10.0.4.0/24)

Currently empty.
Ready for future Load Balancer + Auto Scaling.

Be honest in the interview: Currently, all active resources are in ap-south-1a. The second AZ exists to demonstrate multi-AZ architectural awareness and to satisfy the resume bullet point. In a production system with real traffic, you'd use an Application Load Balancer to distribute across both AZs with Auto Scaling Groups deploying EC2 in each.
What to Say in the Interview

"I provisioned subnets in two AZs — ap-south-1a and ap-south-1b — to demonstrate the multi-AZ architecture pattern. Each AZ is a physically isolated data center. Currently, the EC2 runs in ap-south-1a, but the infrastructure is designed so that adding a Load Balancer and Auto Scaling Group across both AZs would be straightforward — the subnets and route tables are already in place."

Q08
What is high availability and how does your architecture achieve it?
Hard
+
High Availability (HA) means a system continues to function even when individual components fail. It's measured as uptime percentage — 99.9% HA means roughly 8.7 hours of downtime per year. 99.99% means 52 minutes. The goal is to eliminate single points of failure.

HA Principles Applied to CampusCart

  • Multi-AZ subnets: Infrastructure spans 2 AZs. If ap-south-1a data center loses power, ap-south-1b is unaffected.
  • Docker health checks: Each container has a health check. If the Django container crashes, Docker Compose detects it and restarts it automatically.
  • Depends-on with health checks: nginx only starts after web is healthy. web only starts after db and redis are healthy. No cascading failures at startup.
  • Named volumes: PostgreSQL data persists in Docker volumes — EC2 restart doesn't lose database data.
  • Elastic IP: Static IP means DNS never breaks on EC2 restart.

Current Limitations (Be Honest)

  • Single EC2 instance — if the EC2 itself fails, application goes down. True HA would require Auto Scaling Group across both AZs.
  • Single database container — would need RDS Multi-AZ for production database HA.
  • No Load Balancer — a single entry point. ALB would distribute traffic and automatically route away from unhealthy instances.
What to Say in the Interview

"The architecture achieves HA at the infrastructure level through multi-AZ subnet design — subnets in ap-south-1a and ap-south-1b. At the application level, Docker health checks and depends-on conditions ensure the containers start in order and restart on failure. The Elastic IP ensures DNS stability across EC2 restarts. For a v1 production system, this is solid. The natural next step would be an ALB with Auto Scaling across both AZs and RDS Multi-AZ for the database."

EC2 & Compute
Q09
What is an Elastic IP and why is it needed?
Easy
+
An Elastic IP is a static, public IPv4 address that belongs to your AWS account — not to a specific EC2 instance. By default, every time you stop and start an EC2 instance, AWS releases the old public IP and assigns a new one. Elastic IP solves this by giving you a permanent, fixed public IP that survives stop/start cycles.

Why CampusCart Needs It

  • DNS stability: If we point a domain to our EC2's public IP, every restart would change that IP and break DNS.
  • GitHub Actions SSH: Our CI/CD pipeline (Soldier 5) SSHs into the EC2 to deploy. If the IP changes, the SSH command in GitHub Actions would fail on the next deployment after any EC2 restart.
  • Stripe webhooks: Stripe needs to know where to send payment events. A changing IP would break webhook delivery.

How It Works Technically

The Elastic IP is not directly on the EC2's network interface. It lives at the Internet Gateway level. The IGW maintains a 1:1 NAT mapping: Elastic IP ↔ EC2 Private IP (10.0.1.x). Inside the EC2, running ifconfig shows only the private IP. The Elastic IP is transparent to the OS.

AWS Pricing — Know This for Interviews

  • Free: When associated with a running EC2
  • ~$0.005/hour charged when allocated but not associated with any running instance
  • Soldier 6 note: When tearing down, RELEASE the Elastic IP — don't just disassociate it
What to Say in the Interview

"Without an Elastic IP, every EC2 stop/start assigns a new public IP. For CampusCart, this would break DNS, GitHub Actions SSH deployments, and Stripe webhook delivery. I allocated an Elastic IP and associated it with the EC2 — now the IP is permanent and stable. It's free while attached to a running instance, and works at the IGW level through 1:1 NAT — the EC2 OS itself only ever sees the private 10.0.1.x address."

Q11
What is an AMI?
Easy
+
AMI stands for Amazon Machine Image. It's a pre-configured template that contains everything needed to launch an EC2 instance — the operating system, installed software, configuration, and optionally your application. It's like a Docker image, but for virtual machines.

What an AMI Contains

  • Root volume snapshot: The OS disk — Ubuntu, Amazon Linux, Windows, etc.
  • Launch permissions: Which AWS accounts can use this AMI (public, private, shared)
  • Block device mappings: What EBS volumes to attach and their sizes
  • Architecture: x86_64 or arm64 (Graviton)

CampusCart's AMI

AMI ID: ami-0f58b397bc5c1f2e8 Name: Ubuntu Server 22.04 LTS (HVM), SSD Volume Type Region: ap-south-1 (Mumbai) Provider: Canonical (official Ubuntu publisher) Arch: x86_64 Type: HVM (Hardware Virtual Machine) — full virtualization

AMI IDs are region-specific. The same Ubuntu 22.04 in us-east-1 has a completely different AMI ID. This is important when writing cross-region infrastructure scripts.

What to Say in the Interview

"An AMI is a template for launching EC2 instances — it contains the OS, software, and disk configuration. Think of it like a Docker image for VMs. For CampusCart, I used the official Ubuntu 22.04 LTS AMI from Canonical in ap-south-1. When EC2 launches, it copies that AMI onto a fresh EBS volume and boots from it. AMI IDs are region-specific — the same Ubuntu image has different IDs in different regions."

Q12
Why Ubuntu 22.04 LTS specifically?
Easy
+
Every technology choice in a production system should have a reason. Ubuntu 22.04 LTS was not chosen randomly — it was the best fit for CampusCart's requirements across several dimensions.

Every Reason — Be Ready to Defend Each One

  • LTS = Long Term Support: Canonical provides security patches and updates until April 2027 (5 years). Non-LTS Ubuntu versions only get 9 months of support. For a production server, you want years of security updates without forced OS upgrades.
  • Same OS as local dev: Bharath develops on Ubuntu locally. Zero environment mismatch. What works locally works on EC2 — no "works on my machine" problems.
  • Industry standard: Ubuntu is the most widely deployed Linux distro in cloud environments. All AWS documentation, Docker documentation, nginx guides, and DevOps tutorials use Ubuntu examples.
  • apt package manager: Docker, AWS CLI, nginx, Python — all install cleanly via apt. No compilation from source needed.
  • Docker compatibility: Docker officially supports Ubuntu 22.04 and provides first-class packages for it.
  • Free tier compatibility: t2.micro with Ubuntu 22.04 is free tier eligible.
What to Say in the Interview

"Ubuntu 22.04 LTS for three main reasons: first, LTS means 5 years of security updates until 2027, so we don't need to force-upgrade the OS during the project lifetime. Second, it's the same OS I develop on locally — eliminating environment inconsistencies. Third, it's the industry standard for cloud Linux — Docker, AWS CLI, and all tooling we use have first-class Ubuntu support."

Q13
How does SSH work at the network level?
Hard
+
SSH (Secure Shell) is a cryptographic network protocol for secure remote access. It operates on TCP port 22. It uses asymmetric cryptography for authentication and then switches to a faster symmetric cipher for the actual session data. Understanding the handshake is what separates candidates.

The SSH Handshake — Step by Step

  • TCP Connection: Client initiates TCP connection to EC2 on port 22. Security Group must allow inbound port 22.
  • Protocol negotiation: Client and server agree on SSH version and cipher suite.
  • Server host key: Server sends its public host key. First connection: client is asked to verify fingerprint (yes/no). Stored in ~/.ssh/known_hosts.
  • Key exchange (Diffie-Hellman): Client and server negotiate a shared symmetric session key without sending it over the network. This key encrypts all subsequent communication.
  • Authentication: Server sends challenge encrypted with client's public key (from authorized_keys). Client decrypts it using private key (.pem file). Decrypted response proves client has the private key without ever exposing it.
  • Session established: All further communication — commands, output, file transfers — is encrypted with the symmetric session key.

The SSH Command for CampusCart EC2

ssh -i campuscart-key.pem ubuntu@ELASTIC_IP # Breakdown: # -i campuscart-key.pem → use this private key file for auth # ubuntu → default user for Ubuntu AMIs on AWS # ELASTIC_IP → the static public IP we allocated # # What happens at network level: # 1. TCP SYN → EC2:22 (allowed by Security Group) # 2. SSH handshake (host key verification, key exchange) # 3. Auth challenge/response using .pem file # 4. Encrypted session established # 5. You get a shell on the EC2
What to Say in the Interview

"SSH uses asymmetric cryptography for authentication. AWS stores the public key on the EC2 in authorized_keys. I keep the private key in the .pem file. During the handshake, the server sends a challenge encrypted with my public key — only my private key can decrypt it. This proves my identity without ever sending the private key over the network. Then all session traffic is encrypted with a symmetric session key negotiated via Diffie-Hellman."

Q14
What is a .pem file and why chmod 400?
Easy
+
A .pem file (Privacy Enhanced Mail, historical name) is a Base64-encoded file containing a cryptographic key. In AWS's case, it's your RSA or Ed25519 private key in PEM format. It's the "secret half" of the key pair — AWS keeps the public half on your EC2.

Why chmod 400?

Linux file permissions are 3 sets of 3 bits: [owner][group][others]. Each set: read(4), write(2), execute(1).

chmod 400 campuscart-key.pem # 4 = read-only for OWNER # 0 = no permissions for GROUP # 0 = no permissions for OTHERS # # In bits: 100 000 000 # Owner: r-- (read only) # Group: --- (nothing) # Others: --- (nothing) # # SSH will REFUSE to use the key if permissions are too open: # "WARNING: UNPROTECTED PRIVATE KEY FILE!" # "Permissions 0644 for 'campuscart-key.pem' are too open" # "It is required that your private key files are NOT accessible by others."

The SSH client enforces this as a security check. If your private key is readable by other users on the system, they could steal it and access your EC2. The check protects you from accidentally exposing it.

Security Rules for .pem Files

  • Never commit to Git: Add *.pem to .gitignore. One accidental commit and the key is on GitHub forever (even if you delete it, it's in git history).
  • Never share it: Give a colleague access by adding THEIR public key to authorized_keys instead.
  • If lost: Create a new key pair. You'll need to access EC2 another way (AWS console) to update authorized_keys.
  • If compromised: Remove that public key from EC2's authorized_keys immediately.
What to Say in the Interview

"The .pem file contains my RSA private key in PEM format. chmod 400 sets it to read-only for the owner, and no permissions for group or others. SSH enforces this as a security check — if the file is readable by anyone else on the system, SSH refuses to use it and throws an 'unprotected private key file' error. It's a protection against accidentally exposing your private key to other system users."

Q15
What is the difference between an Internet Gateway and a NAT Gateway?
Hard
+
Both handle traffic between your VPC and the internet, but they serve fundamentally different purposes. Understanding both — and when to use each — is a key AWS architecture question.

Side by Side Comparison

AspectInternet GatewayNAT Gateway
Traffic DirectionBidirectional (in + out)Outbound only from private subnets
Used WithPublic subnetsPrivate subnets needing internet access
Inbound from Internet?YesNo
Public IP RequirementResources need public/Elastic IPNo public IP needed on resources

When You'd Use NAT Gateway

If CampusCart used RDS in a private subnet, and that RDS instance needed to download OS patches — RDS can't have a public IP. You'd place a NAT Gateway in the public subnet and route private subnet traffic through it. The NAT Gateway has its own Elastic IP, so outbound traffic appears to come from the NAT Gateway's IP. Inbound internet traffic still cannot reach RDS directly.

"The Internet Gateway enables bidirectional internet access for resources with public IPs in public subnets. Q16
What is the difference between a Security Group and a Network ACL?
Hard
+
Both are firewall mechanisms in AWS, but they operate at completely different layers. Security Groups are attached to instances (or load balancers). Network ACLs are attached to subnets. Understanding both is essential for cloud security interviews.

Key Differences

AspectSecurity GroupNetwork ACL
Applies ToEC2 instances, ENIsEntire subnets
StatefulnessStateful — return traffic auto-allowedStateless — must explicitly allow both directions
RulesAllow only (no deny rules)Allow AND Deny rules
Rule EvaluationAll rules evaluated togetherRules evaluated in order (lowest number first)
Default BehaviorDeny all inbound, allow all outboundAllow all traffic (default ACL)
Typical UseInstance-level firewallSubnet-level extra layer, blocking specific IPs

CampusCart Security Group (Soldier 3's Work)

  • Port 80 (HTTP): Inbound from 0.0.0.0/0 — anyone can access the website
  • Port 443 (HTTPS): Inbound from 0.0.0.0/0 — for future SSL
  • Port 22 (SSH): Inbound from Bharath's IP only — not the whole internet
  • All outbound: Allowed — EC2 needs to call Stripe, apt-get, Docker pull, etc.

Stateful explained: When a user makes a request to port 80, the Security Group allows it in. The response traffic (EC2 → user) is automatically allowed out — you don't need a separate outbound rule for port 80 responses.

What to Say in the Interview

"Security Groups are instance-level, stateful firewalls — if I allow port 80 inbound, the response traffic is automatically allowed outbound. Network ACLs are subnet-level, stateless firewalls — I'd need explicit rules for both directions. For CampusCart, Security Groups are sufficient: port 80 and 443 from anywhere, port 22 restricted to my IP only. Network ACLs would be an additional layer for blocking specific malicious IP ranges at subnet level."

Architecture Decisions
Q17
If AZ ap-south-1a goes down, what happens to your application?
Hard
+
This is a trap question. The honest answer is: the application goes down. The EC2 is in ap-south-1a. If that AZ fails, CampusCart is unavailable. But the key is how you answer — explain what the architecture would need to avoid this, and why it's acceptable for this project stage.

Honest Current State

  • EC2 instance is in ap-south-1a Public Subnet only
  • If ap-south-1a fails: EC2 goes down → all 4 Docker containers stop → CampusCart is offline
  • The Elastic IP stays associated (it's account-level), but there's nothing to route to
  • ap-south-1b subnets exist but have no resources

What True Multi-AZ HA Would Look Like

  • Application Load Balancer: Spans both AZs. Routes traffic to healthy targets. If ap-south-1a goes down, ALB only sends to ap-south-1b.
  • Auto Scaling Group: Launches EC2 instances in BOTH AZs. Desired: 2 instances (1 per AZ). If one fails, ASG launches a replacement.
  • RDS Multi-AZ: Primary in ap-south-1a, standby replica in ap-south-1b. Automatic failover in ~60-120 seconds.
  • ElastiCache Multi-AZ: Redis with replicas across AZs.
🎯
Why This Is Acceptable for CampusCart v1: AZ failures are extremely rare — AWS has had very few in its history. For a portfolio project demonstrating DevOps skills, a single-AZ deployment with multi-AZ infrastructure design is appropriate. The subnets and route tables are already in place to scale to true multi-AZ when needed.
What to Say in the Interview

"Honestly — the application would go down because the EC2 is only in ap-south-1a. True AZ-level fault tolerance requires an Application Load Balancer spanning both AZs with an Auto Scaling Group deploying instances in each. The infrastructure is designed for this — both AZs have public subnets, both have private subnets, route tables are configured — the next step is adding the ALB and ASG. For v1, this tradeoff is deliberate: AZ failures are extremely rare and the cost of multi-instance deployment wasn't justified for a portfolio project."

Q18
Why is the database NOT in the private subnet in this project?
Medium
+
This is another question testing your honesty and architectural awareness. The database is NOT in a private subnet because CampusCart uses Dockerized PostgreSQL running as a container on the EC2 — not AWS RDS. The database and the application are on the same server, inside Docker's internal network.

Current Architecture — Why Docker

  • PostgreSQL runs as a Docker container (postgres:15-alpine) on the same EC2
  • It's isolated inside Docker's internal bridge network (campuscart_network)
  • No port is exposed to the host or internet — only the web container connects to it internally
  • This is actually MORE isolated than an RDS in a private subnet in some ways — no port exposed at all

If We Used RDS Instead — Then Private Subnet

  • RDS is a managed AWS service — it has its own network interface in the VPC
  • It would live in Private Subnet 1 (10.0.3.0/24) — no internet route
  • EC2's Security Group would be allowed to connect to RDS's Security Group on port 5432
  • No one on the internet could ever connect directly to the database
What to Say in the Interview

"PostgreSQL runs as a Docker container on the same EC2 — it's not a separate AWS service, so AWS subnet placement doesn't apply. The database is isolated by Docker's internal bridge network and has no ports exposed to the host. The private subnets (10.0.3.0/24 and 10.0.4.0/24) are designed for managed services like RDS — if we migrated to RDS, it would go there. The private subnets exist and are configured — they're ready when we need them."

Q19
What is the AWS shared responsibility model?
Medium
+
The Shared Responsibility Model defines the boundary of security obligations between AWS and the customer. The simplest way to remember it: AWS secures the cloud. You secure what's in the cloud.

AWS's Responsibility — Security OF the Cloud

  • Physical data center security (guards, cameras, biometrics)
  • Hardware (servers, networking equipment, storage)
  • Hypervisor and host isolation (KVM/Nitro — your EC2 cannot interfere with another customer's)
  • Global network infrastructure (fiber, edge PoPs)
  • Managed services infrastructure (the underlying RDS servers, S3 hardware, etc.)

Your Responsibility — Security IN the Cloud (CampusCart)

  • OS patching: apt-get update && apt-get upgrade — AWS doesn't patch your Ubuntu for you
  • Security Groups: Configuring which ports are open, restricting SSH to your IP only
  • IAM roles: Giving EC2 only the permissions it needs (SSM read, ECR pull) — not admin access
  • Secrets management: Using SSM Parameter Store instead of hardcoding credentials
  • Application security: Keeping Django, Python packages updated. Validating inputs. JWT token security.
  • Git hygiene: .env in .gitignore, never committing secrets or .pem files
What to Say in the Interview

"AWS handles everything physical and below the hypervisor — hardware, data center security, network infrastructure. I'm responsible for everything above: OS patching, application security, network configuration via Security Groups, IAM permissions, and secrets management. For CampusCart, I implement this by using IAM roles with minimal permissions, storing secrets in SSM Parameter Store (not in code), restricting SSH to my IP only, and keeping .env out of version control."

Q20
How would you explain your AWS architecture to a non-technical person?
Medium
+
This question tests your communication skills as much as your technical knowledge. A senior engineer should be able to explain complex systems using simple analogies. The goal is to convey the essential concepts without losing the listener in jargon.

The Building Analogy

Use this explanation in the interview:

The Answer — Speak Exactly This

"Imagine AWS is a massive, secure office building in Mumbai. I rented a private floor in that building — that's my VPC. Nobody else can enter my floor without permission.

On my floor, I divided the space into rooms. Some rooms have windows to the outside world — those are my public subnets, where the web server lives. Other rooms have no windows — those are my private subnets, reserved for sensitive things like databases.

The Internet Gateway is the building's reception desk — it controls who comes in and what goes out. Anyone can visit the web server room, but only I can enter through the back door (SSH) because only I have the key card (.pem file).

The Elastic IP is like a permanent address — even if I temporarily close the office for the night and reopen it next morning, the address doesn't change, and people can always find us.

And I set all of this up in a building that has two separate wings (two availability zones) — so if one wing has a power cut, the other is completely unaffected."

💡
Why this answer is powerful: It covers VPC, public/private subnets, Internet Gateway, SSH security, Elastic IP, and AZ redundancy — all without using a single technical term. Interviewers love this because it proves you truly understand the concepts, not just memorized them.
