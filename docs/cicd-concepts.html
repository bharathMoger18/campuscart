CONCEPT 01

What is CI/CD?

continuous integration · continuous delivery · continuous deployment

🔄The Core Definition

CI (Continuous Integration) means every developer commit automatically triggers a build and test process. The moment code is pushed, a machine builds it and runs tests — without any human starting it. The goal is to detect broken code within minutes, not days.

CD (Continuous Delivery) means the software is always in a deployable state. After CI passes, the artifact (a Docker image in our case) is ready to deploy to production. A human or a button click is still required for the final deployment step.

CD (Continuous Deployment) goes one step further — the deployment to production is also automated. Zero human approval required. Every push to main that passes CI lands in production automatically. This is what CampusCart does.

❌Before CI/CD — Manual Process

  1. Developer finishes feature, has to remember to deploy
  2. SSH into EC2 manually
  3. git pull the changes
  4. docker build the image (on the t2.micro — takes 10+ mins, OOMs)
  5. docker compose up and pray it works
  6. Manually check if the app is running
  7. Forget to deploy on Friday → bug lives in production all weekend

✅After CI/CD — CampusCart Pipeline

  1. git push origin main
  2. GitHub Actions detects the push automatically
  3. GitHub's powerful runner builds the Docker image
  4. Image pushed to ECR with the commit SHA as tag
  5. SSH into EC2 automatically, run deploy.sh
  6. Health check confirms app is live
  7. Developer gets a green checkmark in 3–5 minutes

📋Interview Framing — "70% faster release cycles"

When your resume says "cutting release cycle time by 70%" — here is what that means concretely: before, a deployment required manual SSH, manual docker build (~10 minutes on t2.micro), manual verification. That's 20–30 minutes of developer time, often skipped or deferred. After, git push triggers everything automatically in 3–5 minutes with no developer attention. That's the 70% — and it's conservative.

More importantly: 100% of the remaining 30% is now git, not SSH sessions. The developer never touches the production server directly.

CONCEPT 02

GitHub Actions

github's built-in ci/cd platform · yaml-driven · event-triggered

⚙️What GitHub Actions Is

GitHub Actions is GitHub's built-in CI/CD and automation platform. It lets you define automated workflows in YAML files stored inside your repository at .github/workflows/. When a specified GitHub event occurs (a push, a PR, a schedule, a manual trigger), GitHub spins up a virtual machine and runs your workflow.

No external CI server to maintain. No Jenkins, no CircleCI account, no billing configuration for new developers. The pipeline definition lives in the same repo as the code, reviewed with the same pull requests, versioned with the same git history.

💰Pricing (What Matters for Interviews)

  • Public repos: completely free, unlimited minutes
  • Private repos: 2,000 free minutes/month on Free plan
  • After free tier: Linux runners ~$0.008/minute
  • CampusCart: a full deployment takes ~4 minutes. You could do 500 deployments/month on the free tier

🔁Supported Event Triggers

  • push — code pushed to a branch
  • pull_request — PR opened, updated, merged
  • schedule — cron-style, e.g., every night at 2am
  • workflow_dispatch — manual button in UI
  • release — when a GitHub Release is published
  • issue_comment — when someone comments on an issue
💡
Why not Jenkins or CircleCI? Jenkins requires a dedicated server to maintain, patch, and scale. CircleCI is external — another account, another billing relationship, another login. GitHub Actions is built in. For a portfolio project deploying to a single EC2, GitHub Actions is the correct tool. In interviews, be ready to explain this tradeoff — Actions is not always the right answer for larger organizations (some need self-hosted agents, compliance constraints, etc.).
CONCEPT 03

Workflow Structure

workflow → jobs → steps · sequential vs parallel execution

🏗️Three-Level Hierarchy

Every GitHub Actions workflow follows the same hierarchy. Understanding this deeply is essential — most interview questions about GitHub Actions are really questions about this structure.

workflow (deploy.yml) │ Triggered by: push to main, workflow_dispatch │ Has two jobs running sequentially (due to needs:) │ ├── JOB 1: build-and-push │ Runs on: ubuntu-latest (GitHub-hosted VM) │ Steps run sequentially — each must pass for next to run │ ├── Step 1: actions/checkout@v4 │ ├── Step 2: aws-actions/configure-aws-credentials@v4 │ ├── Step 3: aws-actions/amazon-ecr-login@v2 │ ├── Step 4: docker build (SHA tag + latest tag) │ └── Step 5: docker push (both tags) │ └── JOB 2: deploy Runs on: ubuntu-latest (DIFFERENT VM from Job 1) needs: build-and-push ← only runs if Job 1 succeeded ├── Step 1: actions/checkout@v4 ├── Step 2: Setup SSH key (write PEM, chmod 400, ssh-keyscan) └── Step 3: SSH → git pull → deploy.sh SHA

⚠️Jobs Run in PARALLEL by Default

Without needs:, all jobs in a workflow start simultaneously on separate VMs. This is great for parallelism — run tests and linting at the same time. But you never want to deploy before the build finishes. That's why needs: build-and-push on the deploy job creates a strict dependency. Job 2 waits for Job 1 to fully complete and succeed.

🔴If Any Step Fails...

Steps within a job are sequential. If Step 4 (docker build) fails with a syntax error, Step 5 (docker push) never runs. The job fails, and Job 2 is blocked by needs: — the deploy never happens. This is exactly correct behavior. You never push a broken image or deploy broken code.

CONCEPT 04

GitHub Actions Runners

github-hosted vs self-hosted · ubuntu-latest · ephemeral VMs

🖥️What is a Runner?

A runner is the machine that executes your workflow jobs. When you specify runs-on: ubuntu-latest, GitHub allocates a brand-new virtual machine running Ubuntu 22.04 to run that job. The VM is created at the start of the job and destroyed when it ends. Nothing persists between runs.

GitHub-hosted ubuntu-latest specs: 4 vCPUs, 16 GB RAM, 14 GB SSD. Compare this to the CampusCart EC2 (t2.micro: 1 vCPU, 1 GB RAM). GitHub's runner is 16× more RAM — that's why we build Docker images on the runner, not on EC2.

📦What's Pre-installed on ubuntu-latest

GitHub maintains a large list of pre-installed tools so workflows don't need to install basics from scratch:

Docker Engine Docker CLI Docker Compose v2 git 2.x AWS CLI v2 Python 3.x Node.js LTS curl / wget jq OpenSSH

This is why our workflow doesn't have any "Install Docker" or "Install AWS CLI" steps — they're already there.

Ephemeral = stateless by design. Nothing from one run carries over to the next. Docker images built in Job 1 are NOT available in Job 2's runner — they're on different VMs. That's why Job 1 pushes to ECR (external registry) and Job 2 pulls from ECR on the EC2. ECR is the bridge between jobs.
CONCEPT 05

GitHub Secrets

encrypted key-value store · masked in logs · never exposed

🔐How GitHub Secrets Work

GitHub Secrets is an encrypted key-value store at the repository level. Values are stored using libsodium sealed boxes (public-key cryptography) — GitHub never stores or sees the plaintext after you save a secret. The secret is only decrypted at workflow runtime, inside the runner's secure environment.

In workflow YAML, secrets are accessed via ${{ secrets.MY_SECRET }}. GitHub replaces this expression with the actual value at runtime. Even if you write echo ${{ secrets.AWS_SECRET_ACCESS_KEY }} in a workflow, GitHub's log scrubber replaces the output with ***.

📁Types of Secrets in GitHub

  • Repository secrets — available to all workflows in the repo. What we use.
  • Environment secrets — scoped to a specific deployment environment (staging, production). Needed for environment protection rules.
  • Organization secrets — shared across multiple repos in an organization. Used by large teams with shared credentials.

CONCEPT 06

The github Context

github.sha · github.ref · github.actor · immutable image tags

🔗What the github Context Is

In every GitHub Actions workflow, a github context object is automatically available. It contains metadata about the event that triggered the workflow — the commit SHA, the branch, the actor (who pushed), the repository name. You access it as ${{ github.property }}.

The most important property for CampusCart is github.sha — the full 40-character git commit SHA that triggered the workflow. This is what ties the Docker image in ECR to the exact commit in git.

Why github.sha is the right image tag. It's immutable — a SHA always points to the same code, forever. It's traceable — you can look up any SHA in git log and see the commit message, author, files changed. It's safe to rollback — deploy.sh with a previous SHA deploys the previous version exactly. "latest" has none of these properties. Never use "latest" as your only production tag.
CONCEPT 07

Reusable Actions

uses: · @v4 versioning · official aws-actions · actions marketplace

🧩What "uses:" Means

When you write uses: actions/checkout@v4, you're referencing a reusable GitHub Action published in a public repository. The format is OWNER/REPO@VERSION. GitHub fetches the code from that repository at that version and runs it as part of your step.

Think of it like importing a well-tested library function instead of writing the same logic from scratch. actions/checkout has been tested by millions of workflows, handles edge cases (submodules, LFS, sparse checkout), and receives security updates. Writing your own git clone commands would be less reliable.

📦The Three Actions CampusCart Uses

ActionWhat It DoesAlternative (manual)
actions/checkout@v4 Clones repo into runner workspace, sets git config git clone https://github.com/... . (needs auth token)
aws-actions/configure-aws-credentials@v4 Sets AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY env vars export AWS_ACCESS_KEY_ID=${{ secrets.AWS_ACCESS_KEY_ID }}
aws-actions/amazon-ecr-login@v2 Runs aws ecr get-login-password | docker login, outputs registry URL Multi-line shell script with error handling

🔢Version Pinning Strategies

  • @v4 — Major version tag (what we use). Gets security patches automatically. Never gets breaking changes. Best balance of security and stability.
  • @v4.1.2 — Exact version. Maximum reproducibility. Must manually update for security patches.
  • @abc123f — Full SHA. Maximum security. Immutable — no one can replace the action at that SHA. Required in high-security environments.
  • @main — Never do this. The action maintainer could push breaking changes or malicious code at any time.

🏪GitHub Marketplace

GitHub has a marketplace (github.com/marketplace) with thousands of pre-built actions. Common ones relevant to DevOps:

  • actions/upload-artifact — share files between jobs
  • actions/setup-python — install a specific Python version
  • 8398a7/action-slack — Slack notifications
  • snyk/actions — security vulnerability scanning
CONCEPT 08

Docker Build in CI

build context · layer caching · why NOT build on EC2

🐳What Happens During docker build in CI

The GitHub Actions runner has Docker Engine pre-installed. When our workflow runs docker build -t ... ./campuscart-backend, Docker sends the ./campuscart-backend directory (the build context) to the Docker daemon on the runner. The daemon reads the Dockerfile and executes each instruction to create image layers.

The resulting image exists only in the runner's local Docker cache. It's not in ECR yet — that's what the docker push step does.

✅Why Build on GitHub Runner

  • 4 vCPUs, 16 GB RAM — plenty for pip install + collectstatic
  • Build time: 2–4 minutes for Django image
  • No cost to EC2 resources during build
  • Clean environment every run — no cached cruft from old builds

🔴Why NOT Build on EC2

  • t2.micro: 1 vCPU, 1 GB RAM
  • Django image with C extensions (psycopg2, Pillow) compiles native code — this needs significant RAM
  • pip install can OOM-kill the build on 1 GB RAM
  • Even if it works, it blocks the server for 5–10 minutes
  • Containers serving traffic during build = resource contention

💾Docker Layer Caching in CI

By default, GitHub Actions runners start fresh every run — Docker's layer cache is empty. Every build re-downloads the Python base image and re-runs pip install, even if dependencies haven't changed. This adds 2–3 minutes per build.

The solution is actions/cache with Docker's cache-from/cache-to flags, or using GitHub Actions' built-in cache backend. For CampusCart at this stage, the added complexity (cache invalidation logic, cache keys tied to requirements.txt) isn't worth it. A 4-minute build on a free runner is acceptable. Large production pipelines at companies absolutely implement layer caching to bring builds from 10+ minutes down to 1-2 minutes.

👤IAM: Two Different Identities

GitHub Actions uses the campuscart-github-actions IAM user (created by Soldier 3). This user has exactly one permission: ecr:GetAuthorizationToken + ECR push permissions on the campuscart-web repository. Least privilege — it cannot do anything else in AWS.

The EC2 uses the campuscart-ec2-role IAM role (Instance Profile). This role can pull from ECR, read SSM parameters, and other EC2-specific operations. It cannot push to ECR.

Two identities, two permission sets, zero overlap. Clean security boundary.

💰Data Transfer Costs

  • Push (GitHub Runner → ECR): Inbound to AWS is free. Pushing the image costs nothing.
  • Pull (EC2 → ECR, same region): EC2 pulling from ECR in the same region (ap-south-1) is free — data stays within AWS's network.
  • Layer deduplication: If Python base layer (200 MB) is already in ECR, only the changed application layer (~5 MB) is uploaded per deploy. Very efficient.
CONCEPT 10

SSH Deployment from CI

private key in secrets · ssh-keyscan · stricthostchecking · exit codes

🔌Why SSH? — The Network Reality

GitHub Actions runners run on GitHub's infrastructure — a completely different network from your EC2 in ap-south-1. They cannot directly execute code on your EC2, cannot call your EC2's internal APIs, and cannot use AWS SSM Session Manager (which requires the EC2 to have SSM agent + IAM role configured specifically for it, adding complexity).

SSH is the universal, battle-tested bridge. The EC2 has port 22 open in its security group (Soldier 3). The runner has the private key. One ssh command gets a shell on the EC2 and runs whatever you need.

🔐The SSH Security Model

AWS generates the campuscart-key key pair during EC2 launch (Soldier 2). The public key goes into EC2's /home/ubuntu/.ssh/authorized_keys — it lives on the server. The private key (campuscart-key.pem) is downloaded once and should be stored securely — we put it in GitHub Secrets as EC2_SSH_KEY.

During the SSH handshake: the runner presents the private key, EC2 verifies it matches the public key in authorized_keys, access is granted. The private key never travels over the network in plaintext — only a cryptographic proof that you have it.

✅ssh-keyscan — The Right Way

Before SSHing, we run ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts. This fetches EC2's public host key (fingerprint) and stores it in known_hosts. When SSH connects, it verifies the server's identity against this stored fingerprint — preventing man-in-the-middle attacks.

Without this, SSH would prompt "Are you sure you want to connect?" — which hangs forever in an automated pipeline.

⚠️-o StrictHostKeyChecking=no

This option completely disables host key verification. SSH trusts whatever server answers — even a MITM attacker. We include it as a belt-and-suspenders backup, but the real protection is ssh-keyscan pre-populating known_hosts.

In a stricter production environment, you'd remove this flag and rely solely on known_hosts. For a portfolio EC2 with no sensitive customer data, it's an acceptable trade-off.

🎯Exit Codes — How GitHub Actions Knows Success or Failure

This is one of the most important things to understand. When the runner runs the ssh command, SSH returns the exit code of the remote command (deploy.sh). Soldier 4's deploy.sh exits 0 on success and 1 on failure.

GitHub Actions evaluates every step's exit code. Non-zero exit code = step failed = job failed = workflow run is marked red. The developer who pushed gets a GitHub notification email with a link to the failed logs. And because deploy.sh prints the container logs before exiting 1, the failure is fully diagnosable without ever SSHing into the EC2 manually.

This is the end-to-end reliability chain: deploy.sh exit code → SSH exit code → GitHub step result → job result → workflow result → developer notification.

20 Interview Questions

Every answer uses CampusCart context. Click any question to expand the answer.

Q 1 What is CI/CD and what problem does it solve? +
Complete Answer

CI/CD is a practice that automates the software delivery pipeline. CI (Continuous Integration) means every commit automatically triggers a build and optionally a test run — catching broken code within minutes. CD (Continuous Deployment) means the application is automatically deployed to production after a successful build, with no human intervention required.

The problem it solves for CampusCart: before CI/CD, deploying meant manually SSHing into the EC2, running git pull, building the Docker image on the t2.micro (which takes 10+ minutes and can OOM on 1 GB RAM), restarting containers, and manually checking if the app was live. This was error-prone, time-consuming, and often skipped — meaning bug fixes sat undeployed for days. With the GitHub Actions pipeline, git push origin main triggers the entire process automatically in 3–5 minutes on GitHub's 16 GB RAM runner, with health checks and automatic failure detection.

Q 2 What is GitHub Actions and how does it work? +
Complete Answer

GitHub Actions is GitHub's built-in CI/CD and automation platform. Workflows are defined as YAML files stored in .github/workflows/ inside the repository. When a specified GitHub event occurs — like a push to a branch — GitHub reads the relevant workflow files and executes them on virtual machines it provides called runners.

For CampusCart, when a developer pushes to main, GitHub reads .github/workflows/deploy.yml, spins up an Ubuntu 22.04 virtual machine (ubuntu-latest), and runs the jobs defined in it. The runner has Docker, git, and AWS CLI pre-installed. Our workflow builds the Django Docker image on that runner, pushes it to Amazon ECR, then SSHes into the production EC2 to trigger a container restart with the new image. The entire process is event-driven and requires zero manual steps after the initial setup of GitHub Secrets.

Q 3 What is a workflow trigger? What triggers your pipeline? +
Complete Answer

A workflow trigger is an event that causes a GitHub Actions workflow to execute. It's defined in the on: block at the top of the workflow file. GitHub supports many trigger types: push, pull_request, schedule (cron), workflow_dispatch (manual), release, and more.

CampusCart's pipeline has two triggers. The primary trigger is push filtered to the main branch — every time code is merged to main, the pipeline runs automatically. We specifically exclude pull requests (no pull_request: trigger) because we never deploy unreviewed code to production. Feature branches don't trigger deployments.

The secondary trigger is workflow_dispatch — a manual trigger button that appears in the GitHub Actions UI. This is useful for re-deploying after infrastructure work (for example, if the EC2 was rebooted and containers need restarting), or for the first deployment during Soldier 6 setup, without needing to make a dummy code commit.

Q 4 What is the difference between a job and a step? +
Complete Answer

A job is a unit of work that runs on its own virtual machine (runner). Each job gets a fresh, isolated environment. Jobs in a workflow run in parallel by default — unless you use needs: to create dependencies. Jobs can have their own runs-on — one job could run on ubuntu-latest and another on windows-latest if needed.

A step is a single action within a job. Steps run sequentially within the same VM — they share the job's workspace, environment variables, and filesystem. A step is either a shell command (run:) or a reusable action (uses:). If any step exits with a non-zero code, the remaining steps in the job are skipped and the job fails.

For CampusCart: we have two jobs. Job 1 (build-and-push) has 5 steps — checkout, AWS credentials, ECR login, docker build, docker push — all sharing the same runner and Docker image state. Job 2 (deploy) runs on a completely different VM with its own 3 steps. The jobs communicate via ECR (not via shared filesystem) because they're on separate machines.

Q 5 What does needs: do in GitHub Actions? +
Complete Answer

needs: creates a dependency between jobs. A job with needs: [job-a, job-b] will only start after all listed jobs have completed successfully. If any listed job fails or is skipped, the dependent job is skipped too.

In CampusCart's pipeline, the deploy job has needs: build-and-push. This means: (1) build-and-push must finish before deploy starts — they can't run simultaneously. (2) If build-and-push fails at any step (e.g., docker build fails because of a syntax error in Dockerfile), the deploy job is automatically skipped. We never attempt to deploy an image that wasn't successfully built and pushed to ECR.

This is a critical safety gate. Without needs:, both jobs would start in parallel, and deploy would try to SSH into EC2 and run deploy.sh with a SHA that doesn't exist in ECR yet — the deploy would fail every time. With needs:, the deployment only happens after the image is guaranteed to be in ECR.

Q 6 What are GitHub Secrets and how are they protected? +
Complete Answer

GitHub Secrets is an encrypted key-value store at the repository level (or organization level). Values are encrypted using libsodium public-key cryptography before storage — GitHub's own systems never see the plaintext value after it's saved. Secrets are only decrypted at workflow runtime, inside the runner's secure memory.

In workflow YAML, secrets are accessed via ${{ secrets.SECRET_NAME }}. GitHub replaces this expression at runtime. Even if a developer accidentally writes echo ${{ secrets.AWS_SECRET_ACCESS_KEY }} in a step, GitHub's log scrubber detects the secret value in output and replaces it with ***. Secrets are never visible in workflow logs, PR previews, or to repository collaborators who don't have admin access.

CampusCart uses 6 secrets: AWS IAM credentials for ECR push (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY), AWS region and ECR repo name, and the EC2 SSH key and IP address. The most sensitive is EC2_SSH_KEY — the full content of the private key PEM file that grants SSH access to the production server. Storing it in GitHub Secrets keeps it encrypted and never on disk anywhere except inside a running workflow.

Q 7 How does your pipeline authenticate to AWS? +
Complete Answer

The pipeline uses the aws-actions/configure-aws-credentials@v4 action in Job 1. This action reads the AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY from GitHub Secrets and sets them as environment variables on the runner. All subsequent AWS CLI commands and Docker ECR operations on the runner automatically use these credentials.

These credentials belong to the campuscart-github-actions IAM user — created by Soldier 3's security-setup.sh with a least-privilege policy. The only permissions this user has are ECR-related: ecr:GetAuthorizationToken and ECR push operations on the campuscart-web repository. It cannot launch EC2 instances, read SSM parameters, or do anything else in AWS.

The EC2 itself uses a completely different identity for authentication — the campuscart-ec2-role IAM role attached as an Instance Profile. When deploy.sh on EC2 runs aws ecr get-login-password, it uses the IAM role via the Instance Metadata Service — no static credentials needed on the server. This is the AWS-recommended approach: IAM roles for EC2, IAM users (with access keys) for external services like GitHub Actions.

Q 8 What is github.sha and why do you use it as the Docker image tag? +
Complete Answer

github.sha is a property of the GitHub Actions context object, available in all workflow expressions as ${{ github.sha }}. It contains the full 40-character git commit SHA (e.g., a3f1c9d2e8b4567890abcdef1234567890abcdef) of the commit that triggered the workflow run.

We use it as the Docker image tag for three reasons. First, immutability: a git SHA always refers to the same commit — and by extension, the same Docker image. The tag campuscart-web:a3f1c9d2 will forever mean "the image built from commit a3f1c9d2." Unlike latest, which is overwritten every push. Second, traceability: if the application misbehaves in production, you can run docker inspect on the running container, get the image tag, look up that SHA in git, and see exactly which code is running — commit message, author, files changed. Third, rollback: to rollback to a previous version, you run deploy.sh <previous-sha> with the SHA from the last known-good commit. The image is still in ECR with that SHA tag.

Q 9 Why not use "latest" as the only image tag? +
Complete Answer

Using "latest" as the only production tag is a well-known anti-pattern with three main problems. First, rollbacks become impossible: if you deploy a broken version, "latest" already points to that broken image. You cannot "deploy latest minus one" — latest is a moving pointer, not a version. Second, no auditability: looking at a running container tagged "latest" tells you nothing about which commit is deployed. You can't diagnose production issues without knowing which code is running. Third, caching confusion: Docker may not re-pull "latest" if it thinks it has a cached version — even when ECR has a newer image. Specific SHA tags bypass this because the tag itself is new every push, forcing a fresh pull.

For CampusCart we actually push both a SHA tag and a "latest" tag on every build. The SHA tag is what deploy.sh always uses — this is our production deployment mechanism. The "latest" tag is a convenience for provision.sh's first-run fallback (when GitHub Actions hasn't run yet, provision.sh pulls "latest" to start the app). After initial setup, "latest" is never used for deployment decisions.

Q 10 What is actions/checkout and why is it needed? +
Complete Answer

actions/checkout@v4 is an official GitHub Action maintained by the GitHub team. It clones the repository into the runner's workspace ($GITHUB_WORKSPACE) and checks out the commit that triggered the workflow. Without it, the runner is a blank Ubuntu VM with no knowledge of your repository's files.

For Job 1, checkout is essential: the docker build command needs the Dockerfile and the entire campuscart-backend/ directory as the build context. Without checkout, there's nothing to build. For Job 2, checkout is less strictly required (the deploy step SSHes into EC2 and runs scripts there), but we include it as a good practice — it makes git metadata available (for potential future Slack notifications with commit messages) and keeps the workspace consistent.

The @v4 version pin means we automatically receive bug fixes and security patches within the v4 major version, but breaking changes (which would come as v5) are not automatically applied. This is the standard approach — balance between staying patched and staying stable.

Q 11 How does GitHub Actions SSH into EC2? +
Complete Answer

The deploy job writes the private key from the EC2_SSH_KEY GitHub Secret to a file (~/.ssh/campuscart-key.pem), sets its permissions to 400 (owner read-only, as SSH requires), and runs ssh-keyscan to pre-populate the known_hosts file with EC2's host fingerprint. Then it runs the SSH command: ssh -i ~/.ssh/campuscart-key.pem ubuntu@$EC2_HOST "...".

This works because the corresponding public key was placed in /home/ubuntu/.ssh/authorized_keys on the EC2 when the instance was launched with the campuscart-key key pair (Soldier 2). The SSH handshake uses public-key cryptography: the runner proves it has the private key (by solving a challenge signed with the public key), EC2 verifies the signature against authorized_keys, access is granted. The private key itself never travels over the network.

The GitHub runner and EC2 are on completely different networks — there's no VPN or private connection between them. SSH over port 22 is the bridge. Port 22 is open in the campuscart-sg security group (Soldier 3). EC2's Elastic IP is the public address the runner connects to.

Q 12 What is ssh-keyscan and why is it needed? +
Complete Answer

ssh-keyscan is a utility that connects to a remote host and fetches its SSH public host key (fingerprint), then prints it in a format suitable for adding to ~/.ssh/known_hosts. We run: ssh-keyscan -H $EC2_HOST >> ~/.ssh/known_hosts.

SSH's host key verification is a security feature. The first time you connect to a new host, SSH checks whether its fingerprint is in known_hosts. If not, it prompts: "The authenticity of host X can't be established. Are you sure you want to continue? (yes/no)". In an automated pipeline running on a headless VM, there is nobody to type "yes". The process hangs, waits for input that never comes, then times out — the deployment fails.

ssh-keyscan pre-populates known_hosts before the SSH connection, so when SSH connects it finds the fingerprint there and proceeds without prompting. The -H flag hashes the hostname in the output, which is a security feature — it prevents an attacker who obtains the known_hosts file from learning which hosts you connect to.

Q 13 What happens if deploy.sh fails on EC2? +
Complete Answer

Soldier 4's deploy.sh is designed to fail loudly. Before exiting 1, it prints the last 80 lines of the web container's logs, the last 20 lines of the db container's logs, and the output of docker compose ps -a. All of this output is captured by SSH and displayed in the GitHub Actions workflow log — so the developer sees the failure reason without needing to SSH into EC2 manually.

The container state at failure depends on what went wrong. If the ECR pull failed (wrong SHA, network issue), the old container is still running — no downtime. If docker compose up started but the new container crashed immediately, the old container was already stopped — brief downtime window. This is the limitation of single-node blue-green deployments without a load balancer: there is a brief window during container replacement.

Recovery: fix the code, push to main again, the pipeline runs with a new SHA. If you need to rollback immediately without waiting for a code fix, you can use workflow_dispatch and manually specify a previous known-good SHA — or SSH into EC2 and run ./scripts/deploy.sh <previous-sha> directly.

Q 14 How does GitHub Actions know the deployment failed? +
Complete Answer

Through exit codes. The entire failure detection chain is: deploy.sh uses set -e so any failing command (ECR pull, docker compose up) immediately causes the script to exit. The final health check loop sets a HEALTHY variable; if containers don't become healthy in 150 seconds, deploy.sh explicitly calls exit 1.

The SSH command on the GitHub Actions runner inherits the exit code of the remote command. So if deploy.sh exits 1, the ssh command in the workflow step exits 1. GitHub Actions evaluates each step's exit code — a non-zero exit code marks the step as failed. A failed step causes the job to fail. A failed job is marked red in the GitHub Actions UI, and GitHub sends email notifications to anyone watching the repository.

This exit code chain is what makes CI/CD reliable. Without it, a broken deployment would show as "green" in GitHub — the worst possible outcome. The entire chain from deploy.sh exit 1 → SSH → GitHub step → job → notification is what closes the feedback loop for the developer.

Q 15 What is workflow_dispatch and when would you use it? +
Complete Answer

workflow_dispatch is a GitHub Actions trigger that adds a "Run workflow" button to the Actions tab in the GitHub repository UI. It lets you manually trigger the workflow on demand without making a code commit. You can optionally define inputs on the trigger to accept parameters (e.g., a target environment, a specific image tag to deploy).

For CampusCart, three scenarios where it's useful: First, during initial setup (Soldier 6) — after creating GitHub Secrets, you want to trigger the first deployment without making a dummy code commit. Second, after infrastructure events — if EC2 is rebooted and the containers are down, you want to re-deploy the current main branch immediately. Third, debugging — you changed a GitHub Secret (rotated the AWS access key) and want to verify the pipeline works without touching any application code.

With no inputs: block defined (as in CampusCart), the manual trigger simply runs the workflow on the latest commit of the selected branch with no additional parameters. It always uses the github.sha of the latest commit on the selected branch.

Q 16 How does the pipeline achieve "70% faster release cycles"? +
Complete Answer

The 70% figure comes from comparing the time and friction of manual deployments vs automated ones. Before: a developer finishes a feature, then has to context-switch to deployment — find the PEM file, SSH in, navigate to the app directory, run git pull, run docker compose, watch logs for errors, verify the app is up. This takes 15–20 minutes minimum, often more when troubleshooting build issues on the underpowered t2.micro. And it only happens when someone remembers to do it.

After: the developer pushes code — deployment is automatic, completed in 3–5 minutes on GitHub's runners. The developer doesn't wait for it; they move on and check the result in the GitHub Actions UI at their convenience. The effective time cost to the developer is near zero — git push is part of their normal workflow anyway.

The bigger impact is frequency and reliability: developers now deploy multiple times per day instead of once per sprint, bugs are caught in production earlier, and no deployment ever gets "forgotten." The 70% reduction in time compounds into much larger benefits through more frequent, more reliable releases.

Q 17 How does the pipeline achieve "100% manual deployment effort eliminated"? +
Complete Answer

Once the pipeline is set up and GitHub Secrets are configured, the developer's entire production deployment workflow is: git push origin main. No SSH sessions. No manual docker commands. No checking if containers started. No manually verifying the application URL. Every step from code push to live production is automated by the GitHub Actions workflow.

The pipeline handles: checking out code, authenticating to AWS, building the Docker image, pushing to ECR, establishing SSH connection to EC2, pulling latest code on EC2, pulling the new Docker image, restarting containers, verifying health, and reporting the result. A green checkmark in GitHub means the app is live. A red X means it failed and the logs are in GitHub — still no SSH required to diagnose.

The only manual intervention required is for initial setup (one-time) and for rollbacks in emergencies. Even rollbacks can be automated by adding a rollback workflow that accepts a SHA parameter via workflow_dispatch with inputs:.

Q 18 What is a self-hosted runner vs GitHub-hosted runner? +
Complete Answer

A GitHub-hosted runner is a virtual machine provided and managed by GitHub. You specify runs-on: ubuntu-latest and GitHub spins up a fresh Ubuntu VM for your job, runs it, and destroys it. You pay nothing for maintenance, patching, or provisioning. The VM comes with a large set of pre-installed tools. This is what CampusCart uses.

A self-hosted runner is a machine you own or manage that registers itself with GitHub to accept and run workflow jobs. You install the GitHub Actions runner application on it and it polls GitHub for new jobs. Self-hosted runners are useful when: your EC2 is in a private VPC with no public internet access (so GitHub's runners can't SSH in), you need access to private databases or internal APIs during tests, you need specific hardware (GPUs for ML workloads), or your compliance requirements mandate that code never leaves your infrastructure.

For CampusCart: GitHub-hosted runners are perfect. Our EC2 has a public Elastic IP, our ECR is in AWS, and we don't have compliance constraints. A self-hosted runner would require maintaining another EC2 instance just for CI, which adds unnecessary complexity for a portfolio project.

Q 19 How would you add a test step to this pipeline? +
Complete Answer

The cleanest approach is to add a third job between build-and-push and deploy, or add test steps at the beginning of the build-and-push job. For a Django application, a test step before building the production image would look like: checkout the code, install Python dependencies (pip install -r requirements.txt), set up a test database (PostgreSQL via GitHub Actions' services), run python manage.py test, and only proceed to the build step if tests pass.

In GitHub Actions YAML, this would be a new job: test with runs-on: ubuntu-latest, a services: block to spin up a PostgreSQL container alongside the runner, and steps to install deps and run the Django test suite. Then the build-and-push job gets needs: test, and deploy gets needs: build-and-push. Now the dependency chain is: test → build → deploy. If any test fails, the image is never built and never deployed.

This is what makes CI/CD truly valuable — the "CI" part. Right now CampusCart's pipeline is really just CD (build and deploy). Adding automated tests transforms it into a full CI/CD pipeline where broken code is caught before it reaches production.

Q 20 Walk me through the complete flow from git push to application live. +
Complete Answer — The Full Deployment Flow

Step 1 — Push triggers workflow: Developer runs git push origin main. GitHub detects the push event on the main branch, reads .github/workflows/deploy.yml, and starts the Deploy CampusCart workflow run. GitHub assigns a unique github.sha (the commit SHA) to this run — this SHA will track the image all the way to production.

Step 2 — Job 1 starts on a fresh runner: GitHub allocates an Ubuntu 22.04 VM (ubuntu-latest, 4 vCPU, 16 GB RAM). The 5 steps run sequentially: checkout clones the repo, configure-aws-credentials sets the IAM user env vars, amazon-ecr-login authenticates Docker with ECR (getting a 12-hour token), docker build builds the Django/Daphne image from ./campuscart-backend and tags it with both the SHA and "latest", docker push uploads the image layers to ECR at 021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web:SHA.

Step 3 — Job 2 starts (needs: satisfied): A new, separate Ubuntu VM is allocated. Checkout runs again. The SSH key is written to ~/.ssh/campuscart-key.pem with chmod 400. ssh-keyscan adds EC2's fingerprint to known_hosts.

Step 4 — Deployment on EC2: The runner SSHes into EC2 (ubuntu@ELASTIC_IP) and runs three commands in sequence: cd /app/campuscart → git pull origin main (gets any updated compose files) → ./scripts/deploy.sh SHA.

Step 5 — deploy.sh executes on EC2: EC2's IAM role authenticates to ECR, the new image is pulled (only changed layers downloaded), WEB_IMAGE is exported, docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-build replaces the web container with the new image. Health polling checks for the "healthy" status up to 150 seconds.

Step 6 — Success confirmed: Container becomes healthy, deploy.sh exits 0, SSH exits 0, GitHub step passes, job is marked green, workflow run is complete. Developer sees ✅ in GitHub Actions. Application is live with the new code. Total time: approximately 3–5 minutes. Zero manual steps.
