CONCEPT 01

What is Server Provisioning?

Turning a blank machine into a running application — automatically
The Core Idea

A fresh EC2 instance is just a bare Ubuntu 22.04 machine. It has an IP address, a kernel, and nothing else. It doesn't know what CampusCart is. It has no Docker, no Git, no AWS CLI, no application code. Server provisioning is the process of transforming that blank machine into a fully running application server — installing all required software, configuring the environment, pulling application code, and starting the services.

The question is: do you do this manually by SSH-ing in and typing commands one by one, or do you encode the entire process as a script that runs itself? That choice defines the gap between amateur and professional infrastructure.

❌ Manual Provisioning

  • SSH in, type 30+ commands by hand
  • 30–60 minutes per server setup
  • One typo can break everything
  • Steps live in someone's memory or a Google Doc
  • Next person can't reproduce it reliably
  • Disaster recovery = panic + guesswork
  • Can't audit what was done or when

✅ Automated Provisioning (provision.sh)

  • Run one script: ./provision.sh
  • Under 2 minutes on subsequent runs
  • Zero human error — script is deterministic
  • Steps live in Git — version controlled, auditable
  • Any team member can spin up an identical server
  • Disaster recovery = launch EC2 + run script
  • Every action logged to stdout with timestamps
The "Under 2 Minutes" Claim — Be Honest in Interviews

The resume says "reducing setup time from 30+ minutes to under 2 minutes." This is true but requires explanation. First run (brand new EC2, no Docker cache): takes 5–8 minutes — Docker images need to be downloaded for the first time. Second run onwards (Docker layer cache warm, repo already cloned): truly under 2 minutes, because the script checks what's already done and skips it.

In an interview, say: "The first provision takes 5–8 minutes due to downloading Docker images. Subsequent provisions — like re-provisioning after a config change — run in under 2 minutes because the script is idempotent and Docker's layer cache is warm." This shows you understand the nuance, which is more impressive than just claiming "under 2 minutes."

Why Automation Matters — The Four Pillars

1. Reproducibility: Every environment — dev, staging, production — is built the same way. "Works on my machine" bugs disappear because machines are no longer unique snowflakes.

2. Speed: Disaster recovery goes from hours to minutes. If the EC2 is lost, you launch a new one and run the provision script — application is back in under 10 minutes.

3. Auditability: The script is in Git. You can see exactly what changed, when, and who changed it. Manual setups leave no audit trail.

4. Scale: If CampusCart needed 10 servers instead of 1, you'd run the provision script 10 times — not spend 10 hours SSHing into each one.

CONCEPT 02

Linux at OS Level

Ubuntu 22.04 internals — apt, users, filesystem, permissions
Ubuntu 22.04 — What You're Working With

When AWS launches an EC2 with the Ubuntu 22.04 AMI, you get a Linux system with: kernel 5.15 LTS, systemd as the init system (PID 1), bash as the default shell, and apt as the package manager. The default login user is ubuntu, not root. This user has passwordless sudo access — so you can run privileged commands without setting a root password.

apt-get — The Package Manager

apt-get (Advanced Package Tool) manages software packages on Debian-based Linux. It reads from sources.list — a list of repositories — to know where to download packages from. When you run apt-get update, it fetches the latest package lists from all configured repositories. When you run apt-get install docker-ce, it downloads the Docker package and all its dependencies from the Docker repository.

Why apt-get update first? A fresh EC2 has stale package lists from when the AMI was created (could be months old). Without updating, you might install outdated packages with known security vulnerabilities, or fail entirely because the repository index references a version that no longer exists.

Official Docker Repo vs Ubuntu's Built-in Package — Critical Difference

Ubuntu's own package repositories include Docker, but it's the docker.io package — often 1–2 major versions behind the official release. For example, Ubuntu 22.04 ships Docker 20.x while the current release is Docker 26.x.

The right way: Add Docker's official GPG key and repository from download.docker.com, then install docker-ce (Community Edition). This gives you the current release with the docker compose plugin (v2), which is required for our project. The provision.sh adds Docker's repo to /etc/apt/sources.list.d/docker.list and verifies it with Docker's GPG key before installing.

The /app Directory — Why Here?

Linux has a Filesystem Hierarchy Standard (FHS). Application code conventionally lives in /opt/ or /app/ — not in /home/ubuntu/. Why? /home/ubuntu/ is a user's home directory — it's personal, not a deployment target. If a different user runs the deploy script, they'd need to navigate to someone else's home directory. /app/ is a neutral, shared location for application code — it's clear, predictable, and professional.

We create it as: sudo mkdir -p /app && sudo chown ubuntu:ubuntu /app. The ubuntu user owns it so subsequent commands don't need sudo for the application directory.

File Permissions — chmod +x

In Linux, a file has three permission types: read (r), write (w), execute (x), for three audiences: owner, group, others. By default, a new file is not executable. When you run chmod +x provision.sh, you're adding execute permission — telling Linux "this file can be run as a program." Without this, running ./provision.sh gives "Permission denied" even though you own the file.

ubuntu User vs root User

The root user has UID 0 and unlimited privileges — it can delete system files, kill any process, overwrite anything. Running your entire provision script as root is dangerous and bad practice. The ubuntu user (UID 1000) has limited privileges by default but has passwordless sudo on this EC2. Our script runs as ubuntu and uses sudo only for privileged operations like installing packages and creating system directories. Everything else — cloning the repo, creating .env, running Docker — happens as the ubuntu user.

CONCEPT 03

How Docker is Installed on Linux

Docker architecture, the docker group, and why it all works
Docker's Three-Layer Architecture

Docker is not one monolithic program. It has three distinct components that work together:

dockerd (Docker Daemon): A background service (managed by systemd) that does the actual work — manages images, containers, networks, and volumes. It exposes a REST API on a Unix socket at /var/run/docker.sock.

Docker CLI (docker command): The tool you type commands into. It's just a client — it translates your commands into REST API calls and sends them to dockerd via the socket. When you type docker ps, the CLI calls GET /containers/json on the socket.

containerd: The container runtime that dockerd delegates to. It handles the actual lifecycle of containers — pulling image layers, creating namespaces, running processes. Docker, Kubernetes, and other tools all use containerd under the hood.

Why Docker Needs a Modern Linux Kernel

Docker containers are not virtual machines. They use two Linux kernel features to create isolation:

Namespaces: Each container gets its own view of resources. The PID namespace makes the container think it's the only process (PID 1 inside the container). The network namespace gives each container its own network stack. The mount namespace gives each container its own filesystem view. These exist in the kernel — Docker just uses them.

cgroups (Control Groups): Limit how much CPU, RAM, and disk I/O a container can use. This is how --memory=512m works — the kernel enforces it. Ubuntu 22.04 ships with kernel 5.15 LTS which has full support for all these features. This is why Docker doesn't work on old kernels — the underlying features don't exist.

The docker Group — Why We Add ubuntu To It

The Docker socket (/var/run/docker.sock) is owned by root:docker with permissions 660. Only root or members of the docker group can talk to it. Without adding ubuntu to the docker group, every single docker command requires sudo: sudo docker ps, sudo docker compose up, etc.

In provision.sh: sudo usermod -aG docker ubuntu adds ubuntu to the docker group.

Critical gotcha: The group membership doesn't take effect in the current shell session. The provision script uses newgrp docker or starts a new shell with sg docker -c "docker compose up -d" to use the new group membership without logging out.

Docker Compose v2 — The Plugin, Not the Old Tool

There are two versions of Docker Compose. The old one was a separate Python tool: docker-compose (with a hyphen), written in Python, installed separately. The new one is docker-compose-plugin — a Go binary built into the Docker CLI itself, invoked as docker compose (no hyphen).

Our docker-compose.yml uses Compose v2 syntax (version: "3.9"). We install docker-compose-plugin in provision.sh. This is why we use docker compose up not docker-compose up everywhere in the project.

CONCEPT 04

AWS CLI v2 on EC2

Why no aws configure — the IAM Role does everything automatically
The Magic of IAM Roles on EC2

When you run AWS CLI commands on a personal laptop, you need to run aws configure to store your Access Key ID and Secret Access Key in ~/.aws/credentials. On EC2, you do none of this. Why? Because the EC2 has an IAM Instance Profile attached — campuscart-ec2-profile — which links to campuscart-ec2-role.

The AWS CLI automatically detects it's running on EC2, queries the Instance Metadata Service for temporary credentials, and uses those credentials for every API call. You never touch a credentials file. The IAM Role is the identity — no keys to store, no keys to leak, no keys to rotate manually.

AWS CLI v2 — Why Not apt install awscli?

Ubuntu's package repository includes the AWS CLI, but it's v1 — a Python-based tool that's significantly older. AWS CLI v2 is a compiled Go binary with better performance, better SSM support, and newer features. We download it directly from awscli.amazonaws.com/awscli-exe-linux-x86_64.zip and install it to /usr/local/aws-cli/.

The installation creates a symlink at /usr/local/bin/aws so the aws command works system-wide. You can verify with aws --version — it should say aws-cli/2.x.x.

CONCEPT 05

AWS Instance Metadata Service (IMDS)

The special IP 169.254.169.254 — what it is and why it only works from EC2
What is IMDS?

The Instance Metadata Service is an HTTP endpoint that runs inside every EC2 instance's hypervisor layer. It's reachable at the IP address 169.254.169.254 — but only from within the EC2 instance itself. This IP is a link-local address (169.254.0.0/16 range) — it's non-routable, meaning packets to this IP never leave the host machine. You cannot reach this IP from your laptop or from another EC2.

IMDS knows everything about the instance it's running on: public IP, private IP, instance ID, availability zone, security groups, IAM role credentials, user-data script, and much more.

How provision.sh Uses IMDS

We can't hardcode the EC2's public IP into provision.sh because every new EC2 launch gets a different Elastic IP. Instead, we detect it at runtime:

Getting the public IP from IMDS
# -s = silent (no progress bar), timeout safety added EC2_PUBLIC_IP=$(curl -s --max-time 5 http://169.254.169.254/latest/meta-data/public-ipv4) # Update ALLOWED_HOSTS in the .env file sed -i "s/ALLOWED_HOSTS=.*/ALLOWED_HOSTS=${EC2_PUBLIC_IP}/" /app/campuscart/.env

This means provision.sh works correctly regardless of which Elastic IP is attached. Self-configuring infrastructure.

IMDSv1 vs IMDSv2 — The Security Upgrade

IMDSv1 (old): Anyone inside the EC2 can curl 169.254.169.254 with no authentication and get credentials. This is a SSRF (Server-Side Request Forgery) vulnerability — if the application has an SSRF bug, an attacker can curl the metadata service and steal the IAM credentials.

IMDSv2 (new): Requires a two-step process: first GET a token with a PUT request (specifying TTL), then use that token in the header for metadata requests. SSRF attacks can't easily do PUT requests, so credentials are protected. AWS recommends using IMDSv2. In provision.sh, we use IMDSv1 for simplicity (the Elastic IP endpoint), but for credentials the AWS CLI handles this automatically and uses IMDSv2 when available.

CONCEPT 06

SSM GetParametersByPath

Fetching all 18 secrets in ONE API call and converting them to .env
The Single API Call That Creates the Entire .env

CampusCart has 18 configuration parameters stored in AWS SSM Parameter Store. Instead of making 18 individual aws ssm get-parameter calls — which would mean 18 API round trips, 18 IAM authorization checks, and 18 chances for failure — we fetch them all in one shot:

The single SSM fetch command
aws ssm get-parameters-by-path \ --path /campuscart/ \ --with-decryption \ --recursive \ --region ap-south-1 \ --query 'Parameters[*].[Name,Value]' \ --output text

This returns all 18 parameters as tab-separated name/value pairs, including the encrypted SecureString ones decrypted by KMS.

Why Each Flag Exists — Interview Level
FlagWhat It DoesWhy We Need It
--path /campuscart/Only fetch params under this prefixScopes to CampusCart's params only. Without it we'd get ALL params in the account.
--recursiveFetch all sub-paths under /campuscart/Our params are at /campuscart/KEY_NAME, one level deep. Recursive fetches them all.
--with-decryptionDecrypt SecureString params via KMS6 params are SecureString (DB password, Django secret key, Stripe keys, etc). Without this flag, they come back as ciphertext — useless for .env.
--query 'Parameters[*].[Name,Value]'JMESPath query — extract only Name and Value columnsThe full API response has metadata (version, last modified, ARN, type). We only want name and value.
--output textTab-separated output instead of JSONMakes bash parsing trivial — one tab between name and value, one newline per parameter.
Converting SSM Output to .env — The Bash Parsing

The SSM output looks like this (tab-separated):

/campuscart/DEBUG False /campuscart/DJANGO_SECRET_KEY s3cr3t-v@lue-here /campuscart/DB_PASSWORD mypassword123 ... 15 more lines ...

We need to strip the /campuscart/ prefix and write KEY=VALUE. The bash to do this:

SSM output → .env file conversion
# Fetch all params and write .env in one pipeline aws ssm get-parameters-by-path \ --path /campuscart/ \ --with-decryption \ --recursive \ --region ap-south-1 \ --query 'Parameters[*].[Name,Value]' \ --output text | \ while IFS=$'\t' read -r name value; do # Strip /campuscart/ prefix: "DJANGO_SECRET_KEY" key="${name##/campuscart/}" # Write KEY=VALUE to .env echo "${key}=${value}" done > /app/campuscart/.env

The ## operator is bash parameter expansion — it strips the longest prefix matching the pattern. ${name##/campuscart/} removes /campuscart/ from the start of name.

🔐
Security: The --with-decryption flag only works if the caller has KMS permission. campuscart-ec2-role has kms:Decrypt permission on the CMK that encrypts the SecureString parameters. GitHub Actions' IAM user does NOT have this permission — it can't read secrets, only push Docker images.
GetParametersByPath --with-decryption JMESPath query Bash parameter expansion KMS decryption
CONCEPT 07

Docker Compose Override Files

How docker-compose.prod.yml overrides docker-compose.yml without duplication
The Override Pattern — Don't Repeat Yourself

CampusCart has a docker-compose.yml base file with all 4 services: nginx, web, db, redis. In development, we docker compose up and it builds the Django image from source code. In production, we want everything the same except the web service should pull a pre-built image from ECR instead of building.

Instead of maintaining two separate compose files (duplicating all the nginx, db, redis config), we use an override file: docker-compose.prod.yml that changes only what's different in production.

❌ Two Separate Files

  • docker-compose.yml — full dev config
  • docker-compose.prod.yml — full prod config (copy-paste)
  • Update nginx config? Edit BOTH files
  • Add a new service? Add to BOTH files
  • Files drift apart over time — bugs
  • Violates DRY principle

✅ Base + Override Pattern

  • docker-compose.yml — complete base config
  • docker-compose.prod.yml — ONLY the differences
  • Update nginx? Edit only docker-compose.yml
  • Add service? Edit only docker-compose.yml
  • Single source of truth for shared config
  • Production override is tiny — easy to review
How the Merge Works

When you run docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d, Docker Compose merges the two files. The second file's values override the first. For maps (like environment:), values are merged — the second file adds to or overwrites individual keys. For scalars (like image:), the second file's value replaces the first entirely.

docker-compose.prod.yml — the entire override file
version: "3.9" services: web: build: !reset {} # Remove the build section entirely image: ${WEB_IMAGE} # Use ECR image instead

That's it. Two lines of override. The nginx, db, and redis services remain exactly as defined in docker-compose.yml — the override file doesn't touch them at all.

The WEB_IMAGE Environment Variable Pattern

The ${WEB_IMAGE} in the compose file is an environment variable substitution. Docker Compose reads it from the shell environment when you run the command. In deploy.sh, we export this variable before calling compose:

export WEB_IMAGE="021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web:abc1234" docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-build

This pattern means the image tag (the git commit SHA) flows from GitHub Actions → deploy.sh argument → shell environment → docker-compose.prod.yml → the running container. Fully traceable.

💡
!reset syntax: The !reset YAML tag removes a key defined in the base file. Without it, you'd have both build: and image: set on the web service. Docker Compose can handle this (image takes precedence with --no-build), but !reset is the clean way to remove the build key entirely.
Compose override -f flag merging DRY principle !reset YAML tag ${WEB_IMAGE} variable
CONCEPT 08

ECR Authentication

How docker login works with AWS — tokens, pipes, and the 12-hour window
ECR is a Private Registry — Docker Needs to Authenticate

Docker Hub is public by default — you can pull public images without credentials. ECR is private — every pull and push requires authentication. But ECR doesn't use a username/password like Docker Hub. It uses AWS IAM — which means the authentication flow is uniquely AWS.

Step 1: Get ECR auth token
aws ecr get-login-password --region ap-south-1
↓ AWS STS issues a 12-hour token
Returns a base64 password string (the token)
↓ piped to
Step 2: docker login
docker login --username AWS --password-stdin ACCOUNT.dkr.ecr.REGION.amazonaws.com
↓ Docker stores credentials
Step 3: docker pull / docker push work
for the next 12 hours
The Full ECR Login Command Explained
aws ecr get-login-password --region ap-south-1 | \ docker login \ --username AWS \ --password-stdin \ 021859068764.dkr.ecr.ap-south-1.amazonaws.com

aws ecr get-login-password: Calls the ECR API using the EC2's IAM role credentials. ECR validates the IAM identity and returns a temporary password — a base64-encoded token valid for 12 hours.

| (pipe): The token is piped directly to docker login's stdin. We never store the token in a variable or file — it flows in memory and is immediately consumed by docker login.

--username AWS: Always literally "AWS" — this is the username ECR expects for all token-based auth regardless of who you are.

--password-stdin: Reads the password from stdin (the pipe) instead of a command-line argument. Safer — command-line arguments appear in ps aux output and shell history.

The ECR URL: Format is ACCOUNT_ID.dkr.ecr.REGION.amazonaws.com. This tells docker login which registry to authenticate against — our private ECR in ap-south-1.

Why We Don't Hardcode the Account ID

In deploy.sh, the Account ID is dynamically fetched:

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text) ECR_URI="${ACCOUNT_ID}.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web"

This means the script works correctly even if the code is run in a different AWS account (staging vs production). It's a good habit — don't hardcode account IDs in scripts.

ecr get-login-password 12-hour token --password-stdin IAM-based registry auth ECR URL format
CONCEPT 09

Idempotency in Bash Scripts

Running provision.sh 10 times should produce the same result as running it once
What Idempotent Means

A mathematical term: an operation is idempotent if applying it multiple times produces the same result as applying it once. f(f(x)) = f(x). For bash scripts: running provision.sh 10 times should leave the server in exactly the same state as running it once.

Why does this matter? Network failures happen mid-script. You debug and re-run. You make a config change and re-provision. A non-idempotent script breaks on the second run — "Docker is already installed, can't install again", or worse, duplicates data and silently corrupts the environment.

The Check-Before-Act Pattern

Every step in provision.sh checks if the work is already done before doing it:

# ── Check if Docker is already installed ── if command -v docker &>/dev/null; then echo "[SKIP] Docker already installed: $(docker --version)" else echo "[INSTALL] Installing Docker..." # ... install commands ... fi # ── Check if repo is already cloned ── if [ -d "/app/campuscart/.git" ]; then echo "[SKIP] Repo exists, pulling latest..." cd /app/campuscart && git pull origin main else echo "[CLONE] Cloning repository..." git clone https://github.com/bharathMoger18/campuscart.git /app/campuscart fi # ── .env is always recreated from SSM ── # (intentionally NOT skipped — SSM is the source of truth) echo "[ENV] Fetching config from SSM Parameter Store..."
What We Skip vs What We Always Redo
StepIdempotent BehaviorWhy
Install DockerSkip if already installedRe-installing would fail or downgrade
Install AWS CLI v2Skip if already installedNo need to re-download 50MB binary
Clone repoPull latest if already clonedGet latest code without re-cloning
Create .envAlways recreate from SSMSSM is source of truth — if params changed, .env should update
Set ALLOWED_HOSTSAlways set from IMDSElastic IP could have changed
docker compose upAlways runCompose handles idempotency — only restarts changed services
⚠️
The .env is intentionally always recreated. Even if it already exists, provision.sh overwrites it from SSM. This is correct behavior — if you rotated a secret in SSM and re-provisioned, you want the new value in .env, not the old one. SSM is the single source of truth.

CONCEPT 10

Zero Downtime Deployment

How deploy.sh replaces the running container without dropping requests
What "Near Zero Downtime" Actually Means for CampusCart

CampusCart runs as a single EC2 with Docker Compose — one instance of the web container. True zero-downtime deployment requires at least two instances running in parallel (rolling update). With a single instance, there's a brief window (typically 2–5 seconds) when the old container is stopping and the new one is starting.

What we achieve: near-zero downtime. The deploy process is: pull new image (30 seconds, old container keeps serving) → stop old → start new (2–5 second gap). This is vastly better than the alternative of shutting down and rebuilding on the EC2 (5–10 minutes downtime).

GitHub Actions: push new image to ECR
(old container still running, serving traffic)
↓ SSH into EC2: ./deploy.sh abc1234
ECR login → docker pull
(30–60 seconds, old container still running)
↓
docker compose up -d --no-build
Compose: stop old web → start new web
(~2–5 second gap)
↓
New container running, health check passes
deploy.sh prints: ✓ Deployment complete
The --no-build Flag — Critical for Production

Without --no-build, Docker Compose checks if a build: section exists and rebuilds the image from source code if it does. But wait — we have docker-compose.prod.yml that removes the build: section with !reset. So why do we still use --no-build?

Belt and suspenders. --no-build is an absolute guarantee that Docker Compose will never attempt to build anything, regardless of what's in any compose file. If someone accidentally runs docker compose up -d without the prod override on a t2.micro, --no-build prevents a catastrophic build that would OOM the instance. It's a safety net.

On a t2.micro with 1GB RAM, building a Django Docker image means: installing 50+ Python packages via pip, compiling C extensions (psycopg2 compiles against PostgreSQL headers, Pillow compiles against libjpeg), running collectstatic. This takes 5–10 minutes and can kill the process with OOM (Out of Memory) — leaving the server in a broken state with no running application.

Health Check Verification After Deploy

After starting the new container, deploy.sh waits and verifies the application is actually healthy before declaring success:

# Wait up to 150 seconds (30 attempts × 5 second sleep) echo "Waiting for application to become healthy..." for i in {1..30}; do # Check if the web container is in "healthy" state if docker compose ps --format json | grep -q '"Health":"healthy"'; then echo "✅ Application is healthy! Deployment complete." docker compose ps exit 0 fi echo " Attempt ${i}/30 — waiting 5s..." sleep 5 done echo "❌ ERROR: Container did not become healthy in 150s" docker compose logs --tail=50 web exit 1

If the new container fails to become healthy (bad image, missing env var, crashed app), deploy.sh exits with code 1 — which causes GitHub Actions to mark the deployment as failed. The old container is already stopped at this point, but the health check failure alerts the team immediately.

Docker Health Checks — How the Web Container Knows It's Healthy

In docker-compose.yml, the web service has a health check defined (Soldier 1's work). It periodically runs a command inside the container — typically curl -f http://localhost:8000/health/ or similar. If the command exits 0, the container is "healthy". If it fails repeatedly, the container is "unhealthy" — and if configured with restart: on-failure, Docker automatically restarts it. This is the SRE resume bullet: "implemented Docker health checks to automatically restart failed containers."

Q 01 What is server provisioning and how did you automate it? +
Complete Answer

Server provisioning is the process of taking a blank machine and configuring it into a fully functioning application server — installing required software, setting up the environment, and starting the application.

For CampusCart, I automated this with scripts/provision.sh. A fresh Ubuntu 22.04 EC2 has nothing on it — no Docker, no Git, no application. The script runs 10 steps automatically: system update, Docker installation from the official repo, AWS CLI v2 installation, Git installation, cloning the repository to /app/campuscart, fetching all 18 configuration parameters from SSM Parameter Store in one API call and writing them to .env, detecting the EC2's public IP from the Instance Metadata Service and setting ALLOWED_HOSTS, logging into ECR, and starting the application with docker compose up -d.

Before automation, setting up a server took 30+ minutes of SSH commands. With this script, the operator runs one command and the entire server is configured correctly within minutes — with no human error, no missing steps, and full reproducibility.

Q 02 How does your provision.sh achieve "under 2 minutes" setup time? +
Complete Answer

The "under 2 minutes" is accurate for re-provisioning — when Docker and the repo are already on the server. The first-ever provision takes 5–8 minutes due to downloading Docker images for the first time. I'd always be honest about this distinction in an interview.

The speed comes from three factors: First, the script is idempotent — it checks if each step is already done and skips it. If Docker is installed, it skips the entire Docker installation section. If the repo is already cloned, it just runs git pull. Second, fetching all 18 SSM parameters is a single API call instead of 18 individual calls — this takes about 2 seconds instead of potentially 18 network round trips. Third, the .env is created from SSM in-memory — no waiting for external services except the one SSM call and the IMDS query for the public IP.

The part that can't be made fast on a re-provision is if Docker images need updating — but docker compose up -d only pulls changed images, and with Docker's layer cache, only changed layers are downloaded.

Q 03 How do you retrieve AWS SSM parameters in a bash script? +
Complete Answer

I use aws ssm get-parameters-by-path to fetch all 18 parameters in a single API call. The command fetches everything under the /campuscart/ path prefix, decrypts SecureString parameters via KMS, and returns tab-separated name-value pairs.

The output is piped into a while read loop that strips the /campuscart/ prefix from each parameter name using bash parameter expansion (${name##/campuscart/}) and writes KEY=VALUE lines to /app/campuscart/.env. The entire operation — fetch from SSM and create the .env file — is a single pipeline command, so the sensitive values never touch the filesystem until they're written directly into .env.

The EC2's IAM role (campuscart-ec2-role) has the ssm:GetParametersByPath permission scoped to /campuscart/*, so the AWS CLI automatically uses the role's credentials from the Instance Metadata Service without any aws configure.

Q 04 What is aws ssm get-parameters-by-path and why use it instead of individual get-parameter calls? +
Complete Answer

get-parameters-by-path fetches all parameters whose names begin with a given path prefix, in one API call. For CampusCart, all parameters are stored under /campuscart/, so this returns all 18 at once.

The alternative — get-parameter called 18 times — has several problems: 18 HTTP requests to the SSM API vs 1 (18× the network overhead), 18 separate IAM authorization evaluations, 18 separate KMS decrypt operations for the SecureString params, and 18 opportunities for a transient network failure to break the script partway through, leaving a partially created .env. With a single call, it's atomic — either all 18 come back or none do.

The --recursive flag handles any sub-paths (e.g., if parameters were organized as /campuscart/database/password). The --query flag uses JMESPath to extract only the Name and Value fields, discarding metadata like ARN, version number, and last-modified date that the full API response includes.

Q 05 What is --with-decryption and why is it needed? +
Complete Answer

SSM Parameter Store has two parameter types. String parameters store plaintext — values like DEBUG=False, DB_PORT=5432. SecureString parameters are encrypted at rest using KMS before being stored — the actual value in the database is ciphertext.

CampusCart has 6 SecureString parameters: DJANGO_SECRET_KEY, DB_PASSWORD, EMAIL_HOST_PASSWORD, STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, and VAPID_PRIVATE_KEY. Without --with-decryption, these come back as encrypted ciphertext strings — useless for the application.

When --with-decryption is passed, SSM calls KMS to decrypt these values before returning them. This requires two things: the caller must have kms:Decrypt permission on the CMK used for encryption, and the request must go through the AWS API (it happens server-side, not locally). The campuscart-ec2-role has this KMS permission, which is why provision.sh can fetch decrypted values. The GitHub Actions IAM user does NOT have this permission — it can push Docker images but cannot read CampusCart's secrets.

Q 06 What is the instance metadata service and how do you use it? +
Complete Answer

The Instance Metadata Service (IMDS) is an HTTP endpoint at 169.254.169.254 that is reachable only from within an EC2 instance. It returns data about the instance itself: public IP, private IP, instance ID, availability zone, IAM role credentials, and more. The IP 169.254.x.x is a link-local address — non-routable, which means packets to it never leave the host machine. You can't reach it from your laptop or another EC2.

In provision.sh, I use it to dynamically detect the EC2's Elastic IP: curl -s http://169.254.169.254/latest/meta-data/public-ipv4. This is used to set the ALLOWED_HOSTS variable in the .env file. I can't hardcode this IP because every new EC2 launch gets a different address. By querying IMDS at runtime, the script is self-configuring — it works correctly regardless of which IP is assigned.

The AWS CLI uses IMDS automatically too — when running on EC2 with an attached IAM role, the CLI queries IMDS for temporary credentials without any configuration. This is why provision.sh doesn't need aws configure.

Q 07 How does your deploy.sh script achieve zero manual intervention? +
Complete Answer

deploy.sh takes a single argument — the image tag (the git commit SHA) — and does everything else automatically. GitHub Actions calls it via SSH: ssh ubuntu@ELASTIC_IP './scripts/deploy.sh abc1234'.

The script: validates the argument is present (exits with an error message if not), constructs the full ECR URI using aws sts get-caller-identity to get the account ID dynamically, authenticates with ECR using the IAM role's credentials, pulls the new image, exports WEB_IMAGE as an environment variable, runs docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --no-build which restarts only the web service with the new image, and then polls the container health status for up to 150 seconds, exiting with success when healthy or failure if the container doesn't become healthy in time.

The entire deployment — from GitHub Actions triggering it to the new container running — takes about 2 minutes with no human touch. If it fails, GitHub Actions marks the deployment as failed and the team is notified. No one needs to SSH into the server.

Q 08 What is a Docker Compose override file and how does it work? +
Complete Answer

A Docker Compose override file is a secondary compose file that is merged with the base docker-compose.yml when you pass both with the -f flag. The second file's values take precedence over the first for any keys they both define. Keys in the base file that aren't mentioned in the override remain unchanged.

For CampusCart, docker-compose.prod.yml overrides only the web service to replace the build: directive with an image: directive pointing to the pre-built ECR image. The nginx, db, and redis services are untouched. This means I have one source of truth for all the shared configuration, and production-specific changes are isolated to a tiny 4-line file.

The !reset {} YAML tag removes the build: key from the merged output entirely, so there's no ambiguity. The ${WEB_IMAGE} variable is set in the shell environment by deploy.sh before the compose command runs, carrying the exact ECR image URI with the specific commit SHA being deployed.

Q 09 Why don't you build Docker images on the EC2 in production? +
Complete Answer

CampusCart runs on a t2.micro EC2 — 1 vCPU and 1GB RAM. Building the Django Docker image on this machine would take 5–10 minutes and risks OOM-killing the build process. Here's why: the Dockerfile installs 50+ Python packages, several of which have C extensions that must be compiled — psycopg2 compiles against PostgreSQL headers, Pillow compiles against libjpeg, cryptography compiles Rust code. Compilation is CPU and memory intensive. With only 1GB RAM and the PostgreSQL container also running, the build process frequently runs out of memory and crashes, leaving the server in a broken state.

Instead, GitHub Actions builds the image on a powerful hosted runner (4 vCPUs, 16GB RAM), pushes it to ECR, and the EC2 simply pulls the pre-built image. A docker pull takes 30–60 seconds. The image is consistent — the same binary that was tested in CI is exactly what runs in production. No "it builds differently on EC2" surprises.

The --no-build flag in deploy.sh is an absolute safety net ensuring docker compose never attempts to build anything, even if there's a misconfiguration in the compose files.

Q 10 What is ECR authentication and how does it work? +
Complete Answer

ECR is a private Docker registry — you can't pull images from it without authenticating. Unlike Docker Hub which uses a username/password, ECR uses AWS IAM. The authentication flow is a two-step process.

First, I call aws ecr get-login-password --region ap-south-1. This uses the EC2's IAM role credentials to call the ECR API, which returns a temporary password — a base64-encoded token valid for 12 hours. Second, this token is piped directly to docker login --username AWS --password-stdin ACCOUNT.dkr.ecr.ap-south-1.amazonaws.com. Docker stores this token in its credential store.

After this, any docker pull or docker push to that ECR registry uses the stored token automatically for the next 12 hours. The username is always literally "AWS" — it's how ECR's token-based auth is designed. The password-stdin flag prevents the token from appearing in process lists or shell history.

In deploy.sh, I re-authenticate on every deployment run — this ensures the 12-hour token is always fresh and never expires between deployments.

Q 11 What is idempotency and why is it important in provisioning scripts? +
Complete Answer

An operation is idempotent if running it multiple times produces the same result as running it once. For provision.sh, this means running it 10 times leaves the server in exactly the same state as running it once — no duplicate installations, no corrupted state, no errors.

Every step in provision.sh checks if the work is already done before doing it. Docker installation is skipped if command -v docker succeeds. The repository is not re-cloned if /app/campuscart/.git exists — instead, git pull is run to get the latest code. AWS CLI installation is skipped if the binary already exists.

This matters for several real scenarios: a network failure mid-script means you re-run it — without idempotency, re-running would fail or produce duplicate installations. During debugging, you might run the script several times. If a configuration change requires re-provisioning (e.g., a new SSM parameter was added), the script should safely re-apply everything. The .env file is intentionally always recreated from SSM — it's not skipped — because SSM is the single source of truth for configuration, and a re-provision should pick up any parameter changes.

Q 12 How do you pass environment variables to Docker Compose? +
Complete Answer

CampusCart uses two mechanisms for environment variables in Docker Compose.

First, the .env file. Docker Compose automatically reads a .env file in the same directory as docker-compose.yml for variable substitution within the compose file itself (${VARIABLE} syntax). Additionally, the web service in docker-compose.yml has env_file: .env which passes all variables from .env into the container's environment, so Django can read them via os.environ.

Second, shell environment variables. In deploy.sh, I export WEB_IMAGE in the shell before calling docker compose. Docker Compose reads from the calling shell's environment for variable substitution, so ${WEB_IMAGE} in docker-compose.prod.yml gets the value of the exported variable. This is how the specific ECR image tag flows from the deployment script into the compose configuration without needing to modify any file on disk.

Q 13 What happens to the .env file — where does it come from in production? +
Complete Answer

The .env file is never committed to Git — it's listed in .gitignore. In production, it doesn't exist before provision.sh runs. The script creates it at runtime by fetching all 18 parameters from AWS SSM Parameter Store and writing them as KEY=VALUE lines.

This is by design. Secrets like DJANGO_SECRET_KEY, DB_PASSWORD, and STRIPE_SECRET_KEY should never be in a Git repository — even a private one. SSM Parameter Store is the secure vault. Only the EC2 with the correct IAM role can read these values. The .env file lives on disk only on the production EC2, in /app/campuscart/.env, readable only by the ubuntu user.

Every time provision.sh runs, it recreates .env fresh from SSM. This means if a secret is rotated in SSM, re-running provision.sh picks up the new value automatically. No manual file editing on the server — SSM is always the source of truth.

Q 14 What is the docker group and why is it needed? +
Complete Answer

Docker communicates through a Unix socket at /var/run/docker.sock. This socket is owned by root:docker with permissions 660 — readable and writable only by the root user or members of the docker group.

The Docker daemon (dockerd) runs as root and creates this socket. When you run a Docker command as the ubuntu user, the Docker CLI tries to connect to this socket. Without being in the docker group, ubuntu gets "Permission denied." Every docker command would require sudo — sudo docker ps, sudo docker compose up, and so on.

In provision.sh, I add ubuntu to the docker group with sudo usermod -aG docker ubuntu. Group membership doesn't take effect in the current shell session though — it's only active after logout/login or starting a new session. The provision script handles this by using sg docker -c "docker compose up -d" for the initial compose call, which executes the command in the context of the docker group. After provision.sh completes and the operator logs out and back in, all docker commands work normally without sudo.

Q 15 How does your deploy.sh know which image tag to pull? +
Complete Answer

The image tag is passed as a command-line argument to deploy.sh. The first line after the shebang is:

IMAGE_TAG="${1:?ERROR: Image tag required. Usage: ./deploy.sh <image-tag>}"

The :? bash operator exits the script with the error message if $1 is unset or empty. This is a safety guard — if GitHub Actions calls deploy.sh without an argument due to a CI configuration mistake, the script fails loudly with a clear message instead of silently pulling the wrong image.

The tag itself is the full git commit SHA, generated by GitHub Actions: ${{ github.sha }}. For example, abc1234def5678.... GitHub Actions builds the Docker image tagged with this SHA, pushes it to ECR, and then SSHes into EC2 and calls ./scripts/deploy.sh abc1234def5678. The full ECR URI is then constructed: 021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web:abc1234def5678. Every deployed container is traceable to an exact git commit.

Q 16 What does docker compose up -d --no-build do? +
Complete Answer

Breaking down each part: docker compose up ensures all services defined in the compose files are running. For services already running with the correct image, it does nothing. For services whose image has changed or that aren't running, it starts or restarts them. The -d flag runs everything in detached mode (background) — the command returns immediately without streaming container logs.

The --no-build flag is critical: it explicitly prevents Docker Compose from attempting to build any image from source, even if a build: directive exists in a compose file. This ensures the command only pulls pre-built images from ECR. Without this flag, if there were any compose file misconfiguration or the !reset override didn't apply correctly, Docker Compose might attempt to build the Django image on the EC2 — a 5–10 minute operation that could OOM-kill the instance.

Combined with exporting WEB_IMAGE in the shell environment before this command, Docker Compose reads the variable and uses it to pull the specific ECR image corresponding to the git commit SHA being deployed.

Q 17 How do you verify the application is healthy after deployment? +
Complete Answer

After running docker compose up -d --no-build, deploy.sh polls the container status in a loop — 30 attempts with 5-second sleeps between each (150 seconds total timeout). It checks if the web container's health status is "healthy" by querying docker compose ps --format json.

Docker's health check system is what drives the "healthy" status. The web service in docker-compose.yml has a healthcheck: block that periodically runs a command inside the container. When the container starts, it's in "starting" state. Once the health check command succeeds, it transitions to "healthy." If the health check fails repeatedly, it becomes "unhealthy."

If the container becomes healthy within 150 seconds, deploy.sh prints a success message and exits with code 0 — GitHub Actions marks the deployment as successful. If it doesn't become healthy in time, deploy.sh prints the last 50 lines of container logs (to diagnose the failure) and exits with code 1 — GitHub Actions marks the deployment as failed and the team is notified. This means automated deployment failures are always visible and actionable.

Q 18 What is the difference between docker compose build and docker compose pull? +
Complete Answer

docker compose build reads the build: directive in the compose file (context directory and Dockerfile path), runs docker build, and creates a new local image by executing each Dockerfile instruction — installing packages, copying files, running commands. The result is a new image layer stored in the local Docker image cache. For CampusCart's Django image, this means running pip install, running collectstatic, etc. It uses the local source code as the build context.

docker compose pull reads the image: directive in the compose file, authenticates with the registry if needed, and downloads the specified image from the registry to the local cache. For CampusCart in production, this downloads the pre-built image from ECR. Only new or changed layers are downloaded — layers already present in the local cache are reused.

In production, we exclusively use pull (via up --no-build) and never build. The image is built once by GitHub Actions on a powerful CI runner, pushed to ECR, and pulled to EC2. This ensures what runs in production is byte-for-byte identical to what was tested in CI.

Q 19 If provision.sh fails halfway, what happens when you run it again? +
Complete Answer

Because provision.sh is idempotent, re-running it after a partial failure is safe and correct. Let's say it failed during the AWS CLI installation (Step 3) due to a network timeout. When you re-run it: Step 1 (apt-get update) runs again — harmless, just refreshes the package lists. Step 2 (Docker installation) detects Docker is already installed via command -v docker and skips the entire installation. Step 3 (AWS CLI) detects it's not installed yet and retries the download. Step 4+ continues normally.

The most important case is if it fails during Step 6 (SSM parameter fetch). The .env file might be partially written or not exist at all. On re-run, the entire .env creation step runs again — the file is recreated from scratch from SSM. There's no risk of a corrupted partial .env because the write happens at the end of the pipeline, not incrementally.

This "run it again, it just works" property is the entire point of idempotency in provisioning scripts. It removes the fear of re-running after failures and makes the script suitable for automation — an orchestration system can safely retry it without worrying about side effects.

Q 20 Walk me through what happens from git push to the application being live. +
Complete Answer — The Full Deployment Flow

Step 1 — Git push triggers CI: Developer pushes code to the main branch on GitHub. GitHub Actions detects the push and starts the workflow (Soldier 5's work).

Step 2 — Build Docker image: GitHub Actions checks out the code, configures AWS credentials for the campuscart-github-actions IAM user, and runs docker build on the GitHub-hosted runner — a powerful machine with 4 vCPUs and 16GB RAM. The image is tagged with the full git commit SHA.

Step 3 — Push to ECR: GitHub Actions authenticates with ECR (aws ecr get-login-password) using the GitHub Actions IAM user's credentials, then pushes the image to 021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web:<sha>.

Step 4 — SSH into EC2: GitHub Actions SSHes into the production EC2 using the campuscart-key SSH key stored as a GitHub Actions secret.

Step 5 — deploy.sh runs: ./scripts/deploy.sh <sha> authenticates with ECR (using the EC2's IAM role), pulls the new image, exports WEB_IMAGE, runs docker compose up -d --no-build with both compose files, and polls for container health.

Step 6 — Application is live: The new container becomes healthy, deploy.sh exits 0, GitHub Actions marks the workflow as successful. The entire process takes about 3–5 minutes. Zero manual intervention from developer to live production.
