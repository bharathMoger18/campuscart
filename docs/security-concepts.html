3.1

What is IAM?

Identity and Access Management — the authorization layer for all of AWS
Senior Engineer Says

IAM stands for Identity and Access Management. It is AWS's answer to the fundamental security question: "Who is allowed to do what to which resources?"

Every single API call made to AWS — whether from the console, CLI, SDK, or a service — goes through IAM. No exceptions. IAM is the gatekeeper for all of AWS.

The Four Core Questions IAM Answers
  • WHO is making this request? (Authentication — verifying identity via credentials)
  • WHAT are they trying to do? (The API action — e.g., ssm:GetParameter)
  • WHICH resource are they targeting? (The ARN — e.g., arn:aws:ssm:ap-south-1:...:parameter/campuscart/*)
  • SHOULD they be allowed? (Authorization — checking policies attached to the identity)
IAM Principals — The "Who"

A principal is any entity that can make a request to AWS. There are three types:

  • IAM Users — A person or application with long-term credentials (access key + secret key, or password for console)
  • IAM Roles — An identity without long-term credentials. Assumed temporarily by EC2, Lambda, other services, or cross-account users
  • AWS Services — EC2, Lambda, ECS etc. act as principals when they make API calls on your behalf
Identity-Based vs Resource-Based Policies

Identity-based policies are attached to a principal (user, role, group). They say: "This entity is allowed to do X." Our campuscart-ssm-policy attached to campuscart-ec2-role is an identity-based policy.

Resource-based policies are attached to a resource (S3 bucket, SQS queue, KMS key). They say: "This resource can be accessed by these principals." Example: an S3 bucket policy that says "Allow account B to read this bucket."

CampusCart Context

In CampusCart's AWS setup, we use IAM in two places:

  • EC2 Role (campuscart-ec2-role): Gives the EC2 instance permission to read SSM parameters, pull ECR images, and write CloudWatch logs. The EC2 assumes this role automatically at launch.
  • GitHub Actions User (campuscart-github-actions): Gives CI/CD pipeline permission to push Docker images to ECR. Uses long-term access keys stored in GitHub Secrets.
IAM = Auth Layer for AWS Every API call → IAM Principal + Action + Resource

Why EC2 Uses a Role — Not a User

This is the most common interview question on this topic. The answer has three parts:

  • No credential management: An IAM User would require creating an access key, then SSH-ing it onto the EC2, storing it in ~/.aws/credentials, and manually rotating it every 90 days. A Role eliminates ALL of this — credentials are auto-issued and auto-rotated by AWS.
  • No leakage risk: With a User's access key on the EC2, if someone SSH-es in (or exploits the app), they can cat ~/.aws/credentials and extract permanent credentials. A Role's credentials expire within 1 hour — they're useless after expiry even if stolen.
  • Instance-scoped: A Role is tied to THIS specific EC2 instance. No other machine in the world can use this role unless it's also assigned the Instance Profile. An access key is usable from anywhere on earth.
💡
Interview Answer Pattern: "I use IAM Roles for EC2 because roles provide automatically rotating temporary credentials via the instance metadata service, eliminating the need to manage, store, or rotate access keys on the instance. The campuscart-ec2-role is assumed by EC2 automatically, so the Django application can call SSM and ECR APIs without any hardcoded credentials."
3.3

Principle of Least Privilege

Grant only the minimum permissions needed — nothing more
Senior Engineer Says

The Principle of Least Privilege (PoLP) states: every identity should have only the minimum permissions required to do its job — and nothing more. It is the single most important security principle in cloud infrastructure.

In AWS terms: don't give an EC2 instance AdministratorAccess just because it's "easier." Define exactly what it needs, on exactly which resources, and grant only that.

❌ BAD POLICY — Over-permissive (admin equivalent)
# This gives the EC2 instance GOD MODE — can do ANYTHING to ANY resource { "Effect": "Allow", "Action": "*", ← any AWS API call "Resource": "*" ← any AWS resource in the account } # If EC2 is compromised: attacker can delete your VPC, create admin IAM users, # exfiltrate ALL S3 data, spin up 1000 GPU instances and mine crypto, # delete all your backups. One breach = total account takeover.
✅ GOOD POLICY — campuscart-ssm-policy (least privilege)
# This gives ONLY what CampusCart's EC2 needs { "Effect": "Allow", "Action": ["ssm:GetParameter", "ssm:GetParameters", "ssm:GetParametersByPath"], "Resource": "arn:aws:ssm:ap-south-1:ACCOUNT:parameter/campuscart/*" } ← ONLY /campuscart/* params, ONLY read (no Put, Delete), ONLY ap-south-1 # If EC2 is compromised: attacker can ONLY read /campuscart/* SSM parameters. # They CANNOT: delete resources, access other services, pivot to other regions, # read /other-project/* parameters, or do anything outside SSM read. # Blast radius is contained. The breach is bad but survivable.
CampusCart Least Privilege Breakdown

Here's why each permission in our policy is exactly scoped:

ssm:GetParameter / GetParameters / GetParametersByPath
EC2 needs to READ secrets. We grant GET but not PutParameter, DeleteParameter, or AddTagsToResource.
Resource: arn:aws:ssm:ap-south-1:*:parameter/campuscart/*
(NOT parameter/* — scoped to our project only)
ecr:GetAuthorizationToken
Must authenticate to ECR before pulling images. Must be Resource: * because it's account-level.
Resource: * (unavoidable — GetAuthorizationToken is not resource-specific)
ecr:BatchGetImage + GetDownloadUrlForLayer
EC2 needs to PULL images. We don't grant PutImage or DeleteRepository — EC2 should never push.
Resource: arn:aws:ecr:ap-south-1:*:repository/campuscart-web
(NOT repository/* — only our repo)
logs:CreateLogGroup + CreateLogStream + PutLogEvents
EC2 needs to WRITE logs. We don't grant GetLogEvents or DeleteLogGroup — EC2 can't read or delete logs.
Resource: arn:aws:logs:ap-south-1:*:log-group:/campuscart/*
⚠️
The "Just Use AdministratorAccess" Trap: Developers new to AWS often use the built-in AdministratorAccess managed policy because it's easier. This is a critical security mistake. In an interview, if you say "I attached AdministratorAccess to my EC2," that's an automatic red flag. Always answer: "I created a custom least-privilege policy with only the specific actions and resources the application needs."

IAM Policy Structure

JSON anatomy — every field explained with CampusCart examples
// Complete IAM policy structure — annotated { "Version": "2012-10-17", ← ALWAYS this exact string. It's the policy language version. Never "2008-10-17" (old). Never the current year. "Statement": [ ← Array of permission rules. Each rule is one Statement block. { "Sid": "SSMReadCampusCartParameters", ← Statement ID. Optional. Human-readable name. Appears in CloudTrail logs — useful for auditing. "Effect": "Allow", ← "Allow" or "Deny". DENY always wins over Allow. Default without any policy = implicit DENY (nothing allowed). "Action": [ ← What AWS API operations are permitted. "ssm:GetParameter", ← service:ApiCallName format. Always lowercase service. "ssm:GetParameters", "ssm:GetParametersByPath" ], "Resource": "arn:aws:ssm:ap-south-1:021859068764:parameter/campuscart/*" ↑ Which specific resources these actions apply to. ARN format: arn:partition:service:region:account-id:resource-type/resource-id The * at the end is a wildcard: any parameter under /campuscart/ }, { "Sid": "ECRAuthToken", "Effect": "Allow", "Action": ["ecr:GetAuthorizationToken"], "Resource": "*" ← * required here — this action is account-level, not repo-level } ] }
ARN Format — Broken Down

ARN stands for Amazon Resource Name. It is a globally unique identifier for any AWS resource. Format:

arn : aws : ssm : ap-south-1 : 021859068764 : parameter/campuscart/* ↑ ↑ ↑ ↑ ↑ ↑ ARN partition svc region account-id resource path Partition: "aws" for standard AWS, "aws-cn" for China, "aws-us-gov" for GovCloud Service: ssm, ec2, iam, ecr, logs, s3, kms — lowercase service name Region: ap-south-1 (Mumbai). Some services like IAM are global — region is empty. Account: Your 12-digit AWS account ID, or * for any account. Resource: Depends on service. For SSM: parameter/PATH. For ECR: repository/NAME.
Effect Priority — DENY Overrides ALLOW

IAM evaluation logic (simplified for this level):

  • Default DENY: If no policy exists that explicitly Allows an action, it is DENIED. No permissions = no access.
  • Explicit ALLOW: A policy statement with Effect: Allow grants the permission.
  • Explicit DENY overrides: If ANY policy (even an SCP in AWS Organizations) says Deny, the action is DENIED even if another policy says Allow. DENY always wins.

For CampusCart: our EC2 role has no Deny statements — just carefully scoped Allows. The implicit deny covers everything not explicitly allowed.

Version: Always 2012-10-17 Effect: Allow or Deny DENY always overrides ALLOW Default = Implicit DENY

Instance Profile & IMDS

How EC2 gets credentials without hardcoding them — the full internal flow
Senior Engineer Says

When a developer asks "how does your Django app know its AWS credentials?", the junior answer is "I configured them." The senior answer is: the Instance Metadata Service (IMDS) delivers temporary credentials to any process running on the EC2, and the AWS SDK fetches them automatically on first use.

No configuration needed. No environment variables. No files. It just works — because of the Instance Profile and IMDS working together.

What is an Instance Profile?

An Instance Profile is a container object that holds exactly one IAM Role. It is the bridge between the EC2 API and IAM. AWS requires this indirection for backward compatibility — the EC2 API predates IAM Roles and was never updated to accept role ARNs directly.

In practice: you always name the Instance Profile the same as the Role. For CampusCart: campuscart-ec2-profile contains campuscart-ec2-role.

The Full IMDS Credential Flow — Step by Step

This is what happens when Soldier 4's provisioning script runs aws ssm get-parameters-by-path on the EC2:

1
EC2 launches with Instance Profile attached
--iam-instance-profile Name=campuscart-ec2-profile
AWS records: "this EC2 instance should have credentials for campuscart-ec2-role"
2
AWS injects the Instance Metadata Service (IMDS) endpoint
A magic IP 169.254.169.254 is routable ONLY from inside the EC2.
This is a link-local address — you cannot reach it from outside. Ever.
3
AWS CLI / boto3 / botocore checks for credentials in order:
1. Environment variables → 2. ~/.aws/credentials file → 3. IMDS endpoint
Since we set none of the first two, it reaches IMDS automatically.
4
SDK calls IMDS to discover which role is attached:
GET http://169.254.169.254/latest/meta-data/iam/security-credentials/
Response: campuscart-ec2-role
5
SDK fetches the actual temporary credentials:
GET http://169.254.169.254/latest/meta-data/iam/security-credentials/campuscart-ec2-role
Response: { "AccessKeyId": "ASIA...", "SecretAccessKey": "...", "Token": "...", "Expiration": "2024-..." }
6
SDK uses these credentials for the SSM API call
The credentials are signed into the request headers (AWS Signature V4).
SSM service validates the signature and checks IAM: "Is campuscart-ec2-role allowed ssm:GetParametersByPath on /campuscart/*?" → YES → returns parameters.
7
Credentials expire (typically 1 hour) — SDK auto-refreshes
The SDK checks the Expiration field before each call. If expired or near expiry,
it automatically repeats steps 4-5 to get fresh credentials. Zero manual work.
🔒
IMDSv2 (Instance Metadata Service version 2): The newer, more secure version. Instead of a direct GET, it requires a PUT request first to get a session token, then uses that token in subsequent GET requests. This prevents Server-Side Request Forgery (SSRF) attacks where a malicious web request tricks the app into fetching the metadata endpoint. AWS recommends IMDSv2 for all new deployments.
3.6

Security Groups

Stateful virtual firewall — and why stateful changes everything
Senior Engineer Says

A Security Group is a stateful virtual firewall that operates at the EC2 instance level. Every EC2 instance must belong to at least one Security Group. Every packet traveling to or from the instance is evaluated against the Security Group rules.

The word stateful is the key to understanding Security Groups — and it comes up in every cloud networking interview.

What "Stateful" Means — Connection Tracking

A stateful firewall tracks the state of network connections. If an inbound connection is allowed, the return traffic for that connection is automatically allowed — even without an explicit outbound rule for it.

Example for CampusCart:

  • A browser sends HTTP request to port 80 → Security Group checks inbound rules → Port 80 allowed → Packet reaches Nginx
  • Nginx generates response and sends it back → Security Group sees this is part of an established connection → Automatically allows return traffic — no explicit outbound port 80 rule needed

A stateless firewall (like AWS Network ACLs — NACLs) does NOT track connections. You must explicitly allow both inbound AND outbound for every connection type. This makes NACLs more complex to configure but more granular.

CampusCart Security Group Rules — campuscart-sg
Direction Protocol Port Source/Dest Why
INBOUND TCP 80 0.0.0.0/0 Public web traffic → Nginx. All internet users must reach CampusCart.
INBOUND TCP 443 0.0.0.0/0 Future HTTPS. Open now so Security Group doesn't need editing when SSL is added.
INBOUND TCP 22 YOUR_IP/32 SSH from Bharath's machine ONLY. /32 = exactly one IP. No bots can reach this.
OUTBOUND All All 0.0.0.0/0 EC2 needs to reach ECR, SSM, CloudWatch, apt repos, Stripe API.
Why Port 22 Restriction is Critical

SSH (port 22) is the most attacked port on the internet. AWS research shows that a new EC2 with port 22 open to 0.0.0.0/0 receives its first brute-force attempt within minutes of launch. Bots continuously scan the entire internet for open port 22.

With YOUR_IP/32: bots get TCP connection refused or timeout before the SSH daemon even responds. The attack never gets to password guessing — it's blocked at the network layer.

/32 explained: CIDR notation /32 means all 32 bits of the IPv4 address are fixed. 192.168.1.100/32 = exactly that one IP. /24 = first 24 bits fixed, last 8 variable = 256 addresses. /0 = no bits fixed = all 4 billion IPv4 addresses.

❌ Security Group vs NACL — NACL

  • Stateless — must allow both directions
  • Applies at subnet level (affects all instances in subnet)
  • Rules have priority numbers (evaluated in order)
  • Has explicit ALLOW and DENY rules
  • More complex, more granular

✅ Security Group (what we use)

  • Stateful — return traffic auto-allowed
  • Applies at instance level (per EC2)
  • All rules evaluated together (no priority)
  • Only ALLOW rules (no DENY — implicit deny for everything else)
  • Simpler, most common choice

AWS SSM Parameter Store

Secure, hierarchical config and secrets management — no .env files in production
Senior Engineer Says

SSM Parameter Store is a secure, hierarchical key-value store for configuration data and secrets. It is the correct answer to "how do you manage secrets in production AWS?" — and it replaces .env files, hardcoded values, and manual SSH key transfers.

CampusCart stores 18 parameters in Parameter Store — from Django's secret key to Stripe's webhook secret. The EC2 fetches all of them at startup in one API call. Zero secrets touch disk until runtime.

❌ The .env File Approach

  • Accidentally committed to Git → exposed forever
  • Must be SSH-transferred to every server
  • No audit trail — who read it? Who changed it?
  • Copy-paste errors between environments
  • Plain text on disk — any file read = secret leak
  • Manual rotation = someone remembers to do it

✅ SSM Parameter Store

  • Never in Git — fetched from AWS at runtime
  • Fetched via IAM-authenticated API call
  • Full CloudTrail audit: who, what, when, from where
  • Single source of truth — update once, all instances get it
  • SecureString = KMS-encrypted at rest
  • Value rotation = one AWS CLI command
String vs SecureString — The Decision
TypeStorageUse ForCampusCart Examples
String Plain text, visible in console Non-sensitive config — hostnames, ports, feature flags, public keys DEBUG=False, DB_HOST=db, REDIS_PORT=6379, STRIPE_PUBLISHABLE_KEY
SecureString AES-256 encrypted via KMS Anything causing breach if leaked — passwords, API secret keys, private keys DJANGO_SECRET_KEY, DB_PASSWORD, STRIPE_SECRET_KEY, VAPID_PRIVATE_KEY
Path Hierarchy — /campuscart/* Strategy

The /campuscart/ prefix is not just cosmetic. It enables three powerful capabilities:

  • GetParametersByPath: Fetch all 18 parameters in ONE API call with --path /campuscart/. No need to list each parameter individually.
  • IAM path scoping: Our policy grants access to arn:aws:ssm:...:parameter/campuscart/* — this is the entire path, granting and denying by hierarchy, not by listing individual parameter names.
  • Multi-project isolation: A future project can use /otherproject/* with completely separate IAM rules. CampusCart's EC2 role cannot access those parameters.
# Soldier 4 fetches ALL 18 parameters in ONE command: aws ssm get-parameters-by-path \ --path "/campuscart/" \ --with-decryption \ ← decrypts SecureString params using KMS automatically --region "ap-south-1" \ --query "Parameters[*].{Name:Name,Value:Value}" \ --output json # Output: [ { "Name": "/campuscart/DJANGO_SECRET_KEY", "Value": "abc123...actualkey" }, { "Name": "/campuscart/DB_PASSWORD", "Value": "actualpassword" }, ... 16 more parameters ] # Soldier 4 parses this JSON and writes it to .env on the EC2

AWS KMS & Encryption

How SecureString parameters are encrypted at rest — envelope encryption explained
Senior Engineer Says

KMS stands for Key Management Service. It manages cryptographic keys and handles encryption/decryption operations. When you create a SecureString parameter in SSM, KMS automatically encrypts it — you never handle the encryption yourself. The keys never leave AWS's FIPS 140-2 validated hardware security modules (HSMs).

Envelope Encryption — How KMS Encrypts Your Secrets

KMS uses a technique called envelope encryption. Here's why and how:

Why not encrypt directly with the KMS key? KMS keys can only encrypt small amounts of data (up to 4KB). Secrets can be larger. Also, sending large secrets to KMS for encryption would be slow and expensive. So KMS uses a two-layer approach:

🔑 KMS Customer Master Key (CMK) — lives in AWS HSM, never exported
↓ generates
🗝️ Data Encryption Key (DEK) — generated per parameter, used once
↓ encrypts
🔒 Encrypted parameter value (ciphertext) + Encrypted DEK stored together in SSM
To decrypt: AWS calls KMS to decrypt the DEK → DEK decrypts the ciphertext → plaintext returned over TLS
Who Can Decrypt?

Decryption requires BOTH:

  • SSM permission: ssm:GetParameter with --with-decryption flag
  • KMS permission: kms:Decrypt on the key used to encrypt (our policy grants this implicitly via SSM managed key)

Our campuscart-ec2-role has both permissions. The GitHub Actions user does NOT — it can only push images. Even if GitHub Actions were compromised, it could not read the database password.

💡
Default vs Customer Managed Key: SSM SecureString uses the aws/ssm AWS managed key by default — no cost, no management. For maximum control (custom rotation schedule, cross-account access, CloudTrail key usage logs), you'd create a Customer Managed Key (CMK). For CampusCart at this scale, the default managed key is correct.
3.9

ECR — Elastic Container Registry

Private Docker image registry — why ECR beats Docker Hub for production AWS
Senior Engineer Says

ECR is AWS's fully managed private Docker image registry. It is the AWS-native alternative to Docker Hub. For production deployments on EC2, ECR is the correct choice — same network, IAM authentication, no rate limits, and automatic vulnerability scanning.

❌ Docker Hub (Public Registry)

  • Images public by default (private costs money)
  • Rate limited: 100 pulls/6hr on free tier
  • Separate auth system (not IAM)
  • Data transfer costs from AWS to Docker Hub
  • No native AWS security scanning
  • Credentials stored separately from AWS

✅ AWS ECR (what CampusCart uses)

  • Private by default — IAM controls all access
  • No pull rate limits for ECR
  • Same AWS credentials (campuscart-ec2-role) — no extra login
  • Same region as EC2 — free data transfer, fast pulls
  • Automatic CVE scanning on every push
  • Integrated with CloudTrail for audit logs
Image Tag Immutability — Why It Matters

With tag immutability set to IMMUTABLE on the campuscart-web repository:

  • Once pushed: An image tagged abc1234 (git commit SHA) can NEVER be replaced by a different image with the same tag. The tag is permanent.
  • Forces unique tags: Soldier 5's GitHub Actions pipeline tags every image with the git commit SHA. Each deployment is traceable to an exact code state.
  • Prevents accidents: A misconfigured CI pipeline cannot accidentally overwrite latest with a broken build. The old latest remains intact.
  • Security: An attacker who gains push access cannot silently swap a known-good image with a malicious one under the same tag.
Image Scanning on Push

ECR integrates with Amazon Inspector to scan every Docker image layer for CVEs (Common Vulnerabilities and Exposures) from databases like NVD, RHSA, and ALAS immediately after a push.

For CampusCart, this means: if Django releases a patch for a critical security vulnerability, ECR will flag the old image as having HIGH severity findings. You'll see this in the ECR console and can decide whether to rebuild and deploy.

# ECR URI format for campuscart: 021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web # GitHub Actions pushes with git commit SHA tag (Soldier 5): docker tag campuscart-web:latest \ 021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web:abc1234 docker push 021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web:abc1234 # EC2 pulls the specific tagged image (Soldier 4): docker pull 021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web:abc1234

AWS Shared Responsibility — Security Layer

IAM, Security Groups, and secrets — your responsibility, not AWS's
Senior Engineer Says

The Shared Responsibility Model says: AWS secures the cloud infrastructure. You secure everything you put IN the cloud. For security specifically: AWS handles physical security, hypervisor isolation, and managed-service encryption. You handle IAM policies, Security Group rules, and secrets management.

CampusCart Security Responsibilities
LayerAWS HandlesYou Handle

Network Underlying network fabric, VPC isolation between accounts Security Group rules, NACL rules, VPC route tables, what's publicly exposed
Secrets KMS key security, HSM hardware, SSM service encryption Choosing SecureString for sensitive params, IAM scoping, not putting secrets in code
Container Images ECR infrastructure, S3 storage for layers Image scanning results, base image choices, not running as root in containers
EC2 Instance Hypervisor isolation, physical host security OS patching, SSH key security, Security Group config, what software runs
✅
Interview Answer: "For CampusCart, I'm responsible for the application layer of security: I wrote a least-privilege IAM policy granting only SSM read on /campuscart/* and ECR pull on campuscart-web. I restricted SSH access to my IP only in the Security Group. I stored all 18 application secrets in SSM Parameter Store with SecureString encryption for sensitive values — eliminating all hardcoded credentials. AWS handles the KMS key hardware, the IAM policy evaluation engine, and the physical security of the infrastructure."

20 Security Questions — Answered from CampusCart's Context

Click any question to reveal the complete answer. Every answer references CampusCart's specific resource names, ARNs, and design decisions.

Q 01 What is IAM and why is it important? +
Complete Answer

IAM stands for Identity and Access Management. It is AWS's authorization and authentication layer that controls who can do what to which resources across the entire AWS platform. Every single API call — whether from the console, CLI, SDK, or an AWS service — is evaluated by IAM before it is executed.

IAM is critical because without it, anyone with AWS credentials could do anything to your infrastructure. In CampusCart's setup, IAM ensures that the EC2 instance can read SSM parameters and pull ECR images — but cannot delete EC2 instances, access other projects' data, or make changes to IAM itself. The campuscart-ec2-role is scoped to exactly what the application needs.

IAM also enables the audit trail: CloudTrail logs every API call with who called it, what they called, and when — making security incidents investigatable.

Q 02 What is the difference between an IAM user, role, and group? +
Complete Answer

IAM User: A persistent identity representing a person or application. Has long-term credentials — either a password for console access or an access key + secret key for programmatic access. Credentials do not expire automatically. In CampusCart, I created one IAM User: campuscart-github-actions for the CI/CD pipeline. It uses access keys stored in GitHub Secrets to push Docker images to ECR.

IAM Role: A temporary identity without long-term credentials. Any entity that has permission can "assume" the role, receiving temporary credentials from AWS STS that expire after 1-12 hours. In CampusCart, campuscart-ec2-role is assumed by the EC2 instance automatically. The instance gets auto-rotating temporary credentials via the instance metadata service.

IAM Group: A collection of IAM Users for easier management. Attach a policy to the group and all members inherit it. Not used in CampusCart since there's only one developer account.

Q 03 Why does EC2 use an IAM role instead of an IAM user? +
Complete Answer

Three reasons why campuscart-ec2-role is a Role and not a User:

  • No credential management: An IAM User would require generating an access key, SSH-ing it onto the EC2, storing it in ~/.aws/credentials, and manually rotating it periodically. The Role eliminates all of this — the EC2 gets temporary credentials automatically via the instance metadata service at 169.254.169.254.
  • Auto-rotating credentials: Role credentials expire every 1 hour. If an attacker extracts them from memory, they're useless after expiry. A User's access key is permanent until manually deleted.
  • No static secrets on disk: With a Role, there are no files on the EC2 containing AWS credentials. Nothing to accidentally commit, copy, or leak. The credentials live only in memory during the SDK call.

This is considered a security best practice for any EC2 workload. The approach of putting access keys on EC2 instances is specifically called out by AWS as an anti-pattern.

Q 04 What is the principle of least privilege? Give an example from your project. +
Complete Answer

The principle of least privilege means granting only the minimum permissions required to perform a task — nothing more. In AWS, this means carefully scoping IAM policies to specific actions and specific resources.

In CampusCart, the campuscart-ssm-policy is my concrete example. Instead of attaching AdministratorAccess or even AmazonSSMFullAccess, I created a custom policy with exactly three SSM actions: GetParameter, GetParameters, and GetParametersByPath. And the resource is scoped to arn:aws:ssm:ap-south-1:ACCOUNT:parameter/campuscart/* — only parameters in our project's path, only in Mumbai region.

The practical security impact: if the EC2 instance were compromised, an attacker with campuscart-ec2-role could only read our SSM parameters. They could not create new parameters, delete existing ones, access other projects' parameters, touch EC2 or RDS resources, modify IAM, or do anything outside this narrow scope. The blast radius of a compromise is contained.

Q 05 What is an instance profile and why is it needed? +
Complete Answer

An instance profile is a container object that holds exactly one IAM Role. It is required because the EC2 API predates IAM Roles and only accepts instance profiles — not role ARNs — as a parameter when launching instances.

In practice, you always create an instance profile with the same name as the role and add the role to it. For CampusCart: campuscart-ec2-profile contains campuscart-ec2-role. When running ec2-launch.sh, the --iam-instance-profile Name=campuscart-ec2-profile flag associates this profile (and therefore the role's permissions) with the EC2 instance.

Without an instance profile, the EC2 instance would have no IAM identity. Any attempt by the application to call AWS APIs (reading SSM params, pulling ECR images) would return NoCredentialsError.

Q 06 What is the instance metadata service (IMDS)? +
Complete Answer

The Instance Metadata Service (IMDS) is an HTTP endpoint at 169.254.169.254 that is accessible ONLY from within an EC2 instance. It provides information about the instance itself — including temporary AWS credentials for the attached IAM role.

The IP 169.254.169.254 is a link-local address. It is not routable on the internet and cannot be accessed from outside the EC2. This is a security property — no external party can reach IMDS.

For CampusCart, any time the Django application (via boto3), the AWS CLI in a provisioning script, or Docker pull command needs AWS credentials, the AWS SDK automatically queries IMDS at http://169.254.169.254/latest/meta-data/iam/security-credentials/campuscart-ec2-role and receives temporary AccessKeyId, SecretAccessKey, and SessionToken. These credentials have the permissions of campuscart-ec2-role — exactly the SSM read, ECR pull, and CloudWatch write permissions we defined.

Q 07 How does EC2 get AWS credentials without hardcoding them? +
Complete Answer

Through the Instance Profile and Instance Metadata Service chain: When the EC2 launches with campuscart-ec2-profile attached, AWS knows this instance should have credentials for campuscart-ec2-role.

When any AWS SDK call is made on the EC2, the SDK's credential provider chain first checks environment variables, then ~/.aws/credentials. Since we set neither, it falls through to IMDS. The SDK calls http://169.254.169.254/latest/meta-data/iam/security-credentials/campuscart-ec2-role and receives temporary credentials — AccessKeyId, SecretAccessKey, and SessionToken — that expire in about 1 hour.

The SDK caches these credentials and automatically refreshes them before expiry. From the application developer's perspective: zero configuration needed. Boto3 in Django just works. The AWS CLI just works. Docker ECR login just works. All because of the Instance Profile chain.

Q 08 What is a Security Group? How is it different from a NACL? +
Complete Answer

A Security Group is a stateful virtual firewall operating at the EC2 instance level. Every packet to/from the instance is evaluated against the Security Group's inbound and outbound rules. For CampusCart, campuscart-sg allows inbound TCP 80 and 443 from anywhere, and TCP 22 from my IP only.

The key differences from Network ACLs (NACLs):

  • Stateful vs Stateless: Security Groups track connection state — if inbound port 80 is allowed, the HTTP response automatically flows back out without needing an outbound rule. NACLs are stateless — you must explicitly allow both inbound AND outbound for each connection type.
  • Scope: Security Groups apply per instance. NACLs apply at the subnet level and affect all instances in the subnet.
  • Rules: Security Groups only have ALLOW rules (everything else is implicitly denied). NACLs have numbered ALLOW and DENY rules evaluated in order.
  • Typical use: Security Groups for instance-level protection (what we use). NACLs as a subnet-level backup layer or for explicit DENY rules (blocking a specific IP from an entire subnet).
Q 09 What does "stateful" mean in the context of Security Groups? +
Complete Answer

Stateful means the firewall tracks the state of network connections. When an inbound connection is allowed, the corresponding return traffic for that connection is automatically permitted — without needing an explicit outbound rule.

Concrete CampusCart example: A user's browser opens a TCP connection to the EC2 on port 80. The Security Group's inbound rule allows this. Nginx responds with the HTML page — this is outbound traffic on an ephemeral port. Even though our outbound rule simply says "all traffic allowed," even if we restricted outbound, the Security Group would still allow this specific response because it tracks that this outbound packet is part of an already-established inbound connection.

For CampusCart's EC2, this means we only need to think about what comes IN (which port, from where). The responses automatically follow. This is why Security Groups are much easier to manage than NACLs for most use cases.

Q 10 Why did you restrict SSH to only your IP? What is /32? +
Complete Answer

SSH (port 22) is the most attacked port on the internet. Any EC2 with port 22 open to 0.0.0.0/0 receives automated brute-force attempts within minutes of launch — bots continuously scan the entire IPv4 address space for open SSH ports.

By restricting to MY_IP/32, only my machine's exact public IP can even initiate a TCP connection to port 22. All bot traffic is silently dropped at the Security Group level before it reaches the SSH daemon. The daemon never sees illegitimate connection attempts — they're blocked at the network layer.

/32 in CIDR notation means all 32 bits of the IPv4 address are fixed. In IPv4, an address is 32 bits. A /32 mask means every bit must match — so only that exact single IP address matches. Compare: /24 fixes the first 24 bits (allows 256 addresses), /16 fixes first 16 bits (allows 65,536), /0 fixes nothing (allows all 4+ billion IPv4 addresses).

In security-setup.sh, I auto-detect the current IP with curl -s https://checkip.amazonaws.com so Soldier 6 doesn't need to manually replace a placeholder at execution time.

Q 11 What is AWS SSM Parameter Store? +
Complete Answer

AWS Systems Manager Parameter Store is a secure, hierarchical key-value store for configuration data and secrets. It replaces .env files and hardcoded values in production infrastructure.

For CampusCart, I store 18 application parameters under the /campuscart/ path hierarchy. The provisioning script (Soldier 4) fetches all 18 in a single API call using GetParametersByPath, writes them to a .env file at runtime, and Docker Compose reads that file. No secrets are committed to Git. No secrets are SSH-transferred. Everything is fetched at runtime from SSM via an IAM-authenticated API call.

The path hierarchy also enables granular IAM scoping: campuscart-ec2-role can only access /campuscart/* — not any other project's parameters or AWS-managed parameters.

Q 12 What is the difference between String and SecureString in SSM? +
Complete Answer

String: Stored as plain text. Visible in the AWS console, CLI output without flags, and CloudTrail logs. Appropriate for non-sensitive configuration: hostnames, port numbers, feature flags, public keys.

SecureString: Encrypted at rest using AWS KMS (Key Management Service). The value appears as ciphertext everywhere except when explicitly decrypted with --with-decryption by an entity with both SSM read and KMS decrypt permissions. Appropriate for anything causing a security breach if leaked.

In CampusCart, I use SecureString for 8 parameters: DJANGO_SECRET_KEY, DB_PASSWORD, EMAIL_HOST_PASSWORD, STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET, VAPID_PRIVATE_KEY, and the KMS-encrypted values can only be decrypted by campuscart-ec2-role. Even if someone gained read-only access to SSM without the KMS permission, they'd see ciphertext — useless without the decryption key.

Q 13 How many credentials did you store in SSM and what are they? +
Complete Answer

I stored 18 parameters in SSM Parameter Store under the /campuscart/ path. They cover five categories:

  • Django core (3): DJANGO_SECRET_KEY (SecureString), DEBUG, ALLOWED_HOSTS
  • PostgreSQL (5): DB_NAME, DB_USER, DB_PASSWORD (SecureString), DB_HOST (="db", the Docker service name), DB_PORT
  • Redis (2): REDIS_HOST (="redis", Docker service name), REDIS_PORT
  • Email/Gmail (2): EMAIL_HOST_USER, EMAIL_HOST_PASSWORD (SecureString)
  • Stripe payments (3): STRIPE_SECRET_KEY (SecureString), STRIPE_PUBLISHABLE_KEY, STRIPE_WEBHOOK_SECRET (SecureString)
  • VAPID push notifications (3): VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY (SecureString), VAPID_EMAIL

Of the 18 parameters, 8 are SecureString (KMS-encrypted) and 10 are String. This exceeds the resume claim of "5+ credentials" — 18 is production-level secret management at scale.

Q 14 Why is SSM Parameter Store better than a .env file in production? +
Complete Answer

Four critical advantages for CampusCart:

  • No Git exposure risk: The .env file containing Stripe keys and database passwords cannot be accidentally committed to GitHub because it doesn't exist until runtime. SSM parameters are fetched at provisioning time and written to a temporary .env file that is never in the Git repository.
  • IAM-controlled access: Only principals with ssm:GetParameter permission on /campuscart/* can read these values. That's currently only campuscart-ec2-role. A .env file on disk can be read by any process running as the same user.
  • Audit trail: Every parameter read is logged in CloudTrail: which principal read which parameter, at what time, from which IP. A .env file has no audit trail whatsoever.
  • Centralized rotation: To rotate the database password, I update one SSM parameter. On next instance restart, it picks up the new value. With .env files, I'd have to SSH into every server, edit the file, and restart services manually.
Q 15 What is AWS KMS and how does it protect your SSM SecureString parameters? +
Complete Answer

AWS Key Management Service (KMS) is a managed service for creating and controlling cryptographic keys. It uses FIPS 140-2 validated hardware security modules (HSMs) — physical devices that store master keys and never export them.

For CampusCart's SSM SecureString parameters, KMS uses envelope encryption: when I store STRIPE_SECRET_KEY as SecureString, SSM asks KMS to generate a Data Encryption Key (DEK). SSM uses the DEK to encrypt the secret value with AES-256. Then KMS encrypts the DEK itself with the CMK. Both the ciphertext and the encrypted DEK are stored together in SSM. The plaintext DEK never persists anywhere.

To decrypt: SSM calls KMS to decrypt the DEK (using the CMK in the HSM), then uses the plaintext DEK to decrypt the parameter value, then returns the plaintext over TLS. This happens transparently when Soldier 4 runs the provisioning script with --with-decryption.

The security guarantee: even if someone gained direct database access to SSM's storage, they would only see ciphertext. Without access to the KMS CMK (which requires IAM permission AND is in an HSM), the data is useless.

Q 16 What is ECR and why use it instead of Docker Hub? +
Complete Answer

ECR (Elastic Container Registry) is AWS's fully managed private Docker image registry. For CampusCart, I created the campuscart-web repository at 021859068764.dkr.ecr.ap-south-1.amazonaws.com/campuscart-web.

Why ECR over Docker Hub for this project:

  • Same network: The EC2 in ap-south-1 pulls images from ECR ap-south-1 — same AWS region, same network backbone. This is fast and costs nothing in data transfer.
  • IAM authentication: The EC2's campuscart-ec2-role already has pull permissions via the IAM policy. No separate Docker Hub credentials needed. GitHub Actions' IAM user has push permissions. Access is controlled entirely through IAM.
  • No rate limits: Docker Hub free tier limits pulls to 100 per 6 hours. In a CI/CD pipeline that deploys frequently, this becomes a bottleneck. ECR has no such limits.
  • Vulnerability scanning: ECR automatically scans every image push for CVEs and reports findings by severity — integrated natively, no extra tooling.
Q 17 What is image tag immutability and why is it a security best practice? +
Complete Answer

Image tag immutability means that once an image is pushed with a specific tag, that tag cannot be overwritten by a different image. I set the campuscart-web ECR repository to IMMUTABLE.

Without immutability, this attack is possible: someone pushes a malicious image as latest, overwriting the known-good production image. On the next deployment, EC2 pulls latest — which is now the malicious image — and CampusCart is compromised. With immutability, this is impossible. Once latest is set, it cannot be changed. Any new image requires a new tag.

For CampusCart's CI/CD pipeline (Soldier 5), GitHub Actions tags every image with the Git commit SHA — e.g., abc1234. This means every deployed image is traceable to an exact commit. If there's a production incident, I can check which commit SHA is deployed, review that exact code, and roll back to a previous known-good SHA. Immutability makes this rollback reliable — the previous tag will always point to the exact same image it did when it was first pushed.

Q 18 What permissions does your GitHub Actions IAM user have and why only those? +
Complete Answer

The campuscart-github-actions IAM User has exactly seven ECR permissions, scoped to the campuscart-web repository only:

  • ecr:GetAuthorizationToken on * — required to get a Docker login token for ECR (account-level, can't scope to a repo)
  • ecr:BatchCheckLayerAvailability — check which image layers already exist (avoids re-uploading identical layers)
  • ecr:GetDownloadUrlForLayer — needed for layer deduplication during push
  • ecr:BatchGetImage — retrieve image manifest
  • ecr:PutImage — actually push the image manifest
  • ecr:InitiateLayerUpload, UploadLayerPart, CompleteLayerUpload — multipart upload for image layers

What it deliberately cannot do: read SSM parameters (GitHub Actions runs in GitHub's cloud — secrets stay in AWS), create or delete EC2 instances, modify IAM policies, delete ECR images, or access any service outside ECR. Even if the GitHub repository were compromised and CI/CD credentials were stolen, an attacker could only push images to our ECR — a contained blast radius.

Q 19 If your EC2 was compromised, what damage could an attacker do with your IAM role? +
Complete Answer

With campuscart-ec2-role, an attacker on the compromised EC2 could:

  • Read all 18 SSM parameters under /campuscart/* including SecureString values — so they could get the database password, Stripe keys, etc.
  • Pull Docker images from the campuscart-web ECR repository
  • Write log events to CloudWatch log groups under /campuscart/*

What they cannot do: delete or modify infrastructure, access SSM parameters outside /campuscart/*, push images to ECR, access S3, RDS, Route53, or any other service, create new IAM users or roles, pivot to other AWS accounts, or take actions in any other region beyond ap-south-1.

This is least privilege working as intended. The breach is serious (Stripe keys and DB password are exposed), but it's contained. The attacker cannot destroy infrastructure, access other customers' data (if multi-tenant), or perform privilege escalation within AWS. Compare this to an AdministratorAccess role — that would be total account compromise.

Q 20 What is the difference between authentication and authorization in AWS? +
Complete Answer

Authentication: Verifying that a request comes from who it claims to be. In AWS, this is done via AWS Signature V4 — every API request is cryptographically signed with the caller's credentials (access key or temporary session token). AWS verifies the signature to confirm the identity is legitimate. For CampusCart's EC2, the temporary credentials from IMDS are used to sign API calls — AWS verifies these signatures against the STS-issued token.

Authorization: Determining whether the authenticated identity is allowed to perform the requested action. This is IAM's job. After confirming the request is genuinely from campuscart-ec2-role, IAM checks: does this role have permission to call ssm:GetParameter on arn:aws:ssm:ap-south-1:...:parameter/campuscart/DB_PASSWORD? It evaluates all attached policies and returns Allow or Deny.

In CampusCart's flow: the EC2 signs a request with IMDS-provided credentials (authentication) → AWS verifies the signature and confirms this is campuscart-ec2-role → IAM evaluates campuscart-ssm-policy and finds ssm:GetParametersByPath allowed on /campuscart/* → request proceeds (authorization). Both must succeed for the API call to work.
